- **v1.3**：「页面/模块总体关系图」从单张粗粒度示意图改为强制详细建模：要求逐页面/逐路由（而非归类汇总节点）、按业务域/分层用 subgraph 组织，边上标注实际接口路径或调用符号，节点数超限时拆分为多张关系图（按层级或域）而非退化为概括节点；相应放宽其余章节的篇幅要求。（该版本的 12 节文档结构已在 v2.0 中废弃，细节仅作历史参考）

- **v1.1**：新增「分页面数据流转图」、「模块说明清单」、文档末尾「修改历史」记录；输出位置固定为仓库根目录 `docs/project-cloud-map.md`；再次生成时强制先读取已有文档作为基线做增量更新。
- **v1.0**：初始版本。

## 目标与边界

读取项目当前代码快照（或用户指定的单个文件），生成一张以 Mermaid 为核心的可审阅云图，用于两类场景：

1. **查上下文**：新增或修改需求前，先在云图里定位相关节点及其调用关系，确认影响范围、要改哪些文件/函数。
2. **留痕**：需求改完后，在云图对应节点上追加一条变更记录，让后续查图的人知道"这个节点什么时候被谁改过、改了什么"。

只描述当前代码快照，不读取、调用或推断 Git 历史（commit、branch 历史、tag、blame、diff、提交时间）；允许读取**当前所在分支名称**，仅用于标注变更日志条目的来源分支。这是只读分析 Skill（对业务代码本身只读，不修改业务代码/配置），但云图文档本身需要被创建、增量更新或追加变更记录。

**置信度标签（强制）**：结论标注以下三级之一：
- `confirmed`：已直接读到定义与调用两端的代码证据。
- `inferred`：有部分证据支持但未读到直接调用链路，且完成反向校验仍无法升级为 confirmed。
- `unconfirmed`：完成最低回溯检查（见步骤 4a）后仍未找到数据来源。

**两种工作模式**：

| 模式 | 触发方式 | 节点粒度 | 输出路径 |
|---|---|---|---|
| 项目级 | 用户要求"生成项目云图/项目地图"等，未指定具体文件 | 页面/路由/服务入口/命令/公共导出（不细到函数内部） | `docs/project-cloud-map.md`，超量拆分到 `docs/cloud-map/<域名>.md` |
| 文件级 | 用户指定某个具体文件要求"看这个文件的函数关系/生成这个文件的云图" | 该文件导出的函数/方法/类，及其直接调用的内部函数；文件外部的调用方/被调用模块作为边界节点标注"外部: 路径" | `docs/cloud-map/files/<文件路径短横线化>.md`（如 `server/src/services/orderService.ts` → `docs/cloud-map/files/server-src-services-orderService.md`） |

两种模式共享下方的执行流程、变更日志机制和输出格式，仅节点粒度和扫描范围不同。

## 执行流程

1. **确定模式与范围**：项目级则读取完整目录树、源码、配置、入口；文件级则只读目标文件本身，再追加读取：① 该文件的直接导入/导出关系（找出谁调用了它、它调用了谁），② 若该文件所属业务域已有项目级云图，读取对应节点作为上下文（不强制要求项目级云图必须先存在）。记录扫描和排除范围（node_modules、构建产物、历史目录、测试文件视为排除项逐一说明原因）。
2. **项目级**：根据证据判断类型 Web/全栈/后端/CLI/库，证据不足或矛盾时列候选类型询问用户，不得擅自选定。**文件级**：跳过类型判断，直接进入拆分。
3. 按模式拆分节点：项目级按页面/路由/服务入口/业务域用 subgraph 组织；文件级按函数/方法/类用 subgraph 按"导出函数/内部辅助函数/外部依赖"分组。模块角色统一用技术无关抽象描述（入口/状态或参数/业务逻辑/数据访问或外部集成/响应与渲染），不强求特定目录命名。
4. 对每个节点追踪：触发者/调用者 → 节点自身逻辑 → 调用的下游节点 → 数据访问或外部系统 → 返回/副作用。记录权限分支、异步边界、错误处理、共享状态。
   **4a. 最低回溯深度（判定 unconfirmed 前必须完成）**：① 检查生命周期钩子或入口函数；② 检查 props/参数/上下文订阅；③ 检查同域结构相似节点是否有可复用模式。三类均无发现才可标注 `unconfirmed`。
5. **关系图建模（核心，强制）**：生成 Mermaid flowchart，要求见「输出格式」第 2 节。每条边标注真实接口路径/函数名/调用符号，无证据的分支不得臆造。`inferred` 结论须至少一次反向校验（从被调用方向上查调用者、从数据模型反查写入来源等），成功则升级为 `confirmed`，失败则保留 `inferred` 并注明已尝试的校验方式。
6. **确定当前分支与基线文档**：读取对应输出路径的文档是否已存在。
   - 已存在：完整读取作为基线。关系图按节点增量更新（见「变更记录工作流」），不得删除已有节点或已有变更日志条目；非图内容（文件索引、未确认项）按本次扫描结果覆盖更新。
   - 不存在：首次生成，所有节点变更日志的第一条记录即为该节点的创建记录。
   - 获取当前代码分支名（只读分支查询，不读取提交历史）；无法获取时记为"未知分支"。

## 变更记录工作流

这是本 Skill 区别于普通架构图生成的核心机制：**变更记录挂在节点上，不写在文档末尾的大列表里**。

**节点与变更日志子节点的关系**：每个关系图节点（页面/路由/函数等）可以有一个与之对应的变更日志子节点，用虚线 `-.->|"变更记录"|` 连接，形状统一为 Mermaid 子程序框 `[[...]]`（与普通矩形节点 `[]`、权限菱形 `{}`、数据存储圆柱 `[()]` 区分）。变更日志子节点内容格式为逐行文本（用 `\n` 分隔），每行一条：

```text
日期 分支 变更类型: 内容
```

变更类型枚举：新增 / 变更 / 修复 / 重构 / 移除。条目按时间从旧到新追加，**不得删除或改写已有条目**，即使该节点后续被移除，也应保留"移除"记录而不是整个删掉节点和日志。

**新增需求时**：

1. 读取现有云图（项目级主文档或对应文件级子文档）作为基线。
2. 在关系图中定位新功能的上下文：顺着调用链找直接相关的上游（谁会触发它）和下游（它要调用谁）节点。
3. 分两种情况：
   - **找到强关联节点**（上下游调用关系明确，如新接口挂在已有路由文件下）：新增节点并用实线接入已有调用链，新节点挂一个新的变更日志子节点，首条记录写 `日期 分支 新增: 功能描述`。
   - **无直接关联**（全新模块，如新开一个业务域）：新增独立节点/独立 subgraph，同样挂变更日志子节点，首条记录写 `日期 分支 新增: 功能描述`，并在图注说明该节点暂无上下游关联。
4. 不改动任何已有节点的既有变更日志内容，只做新增。

**变更需求时**：

1. 在现有关系图中定位该需求对应的既有节点（优先精确匹配文件路径/函数名/路由路径）。
2. 向该节点的变更日志子节点**追加**一行：`日期 分支 变更: 需求变更内容`；若该节点还没有变更日志子节点（例如是历史遗留节点），先创建一个，首条记录可以补记为 `日期 分支 变更: 内容（原节点创建时间未记录）`。
3. 若本次变更新增/移除了节点间的调用关系边：同步更新图中的边，并在该节点变更日志追加一行说明，如 `日期 分支 变更: 新增对X的调用` 或 `日期 分支 移除: 不再调用Y`。移除边不代表删除对方节点，除非对方节点确实被整体删除（此时对方节点也要走下方"节点移除"流程，不能直接从图中消失不留痕）。

**节点被整体移除时**：不删除节点，而是保留节点但在变更日志追加 `日期 分支 移除: 原因`，并可在节点样式上用注释标注"已废弃"（不强制改变形状，避免与权限菱形等语义形状混淆）。

**修复/重构同理**，变更类型分别记为 `修复`/`重构`。

## 输出格式

每份云图文档（项目级主文档、项目级拆分子文档、文件级文档）统一包含以下 4 节：

1. **范围与模式**：一句话说明本文档是项目级还是文件级、扫描/读取范围、排除项及原因；若项目级识别类型置信度低且已询问用户，记录确认结果。
2. **关系图（核心，强制）**：Mermaid flowchart，要求：
   - **节点粒度**：项目级到页面/路由/服务入口级，文件级到函数/方法/类级，禁止合并为"N个页面"之类的概括节点。
   - **用 subgraph 按分层/分域组织**，使读者能看出节点所属层次。
   - **边标注真实依据**：接口路径、函数名、调用符号，不写无依据的"调用"字样。
   - **权限/鉴权判断节点统一菱形样式**，与普通节点区分，文字注明判断依据。
   - **变更日志子节点**：按「变更记录工作流」规则，用子程序形状 `[[...]]` + 虚线连接，只在节点确有变更记录时才挂出（避免给从未变更过的节点强行挂空日志框）。
   - **节点数超过约 25 个时拆分为多张图**（按层级或业务域），不得为了塞进一张图而把节点概括粗化；拆分图并列在本节同一标题下。
   - 非 `confirmed` 的边/节点需标注 `inferred`/`unconfirmed`。
3. **文件/符号索引**（精简列表）：按目录分组列出关键文件与导出符号，不逐一展开说明文字。
4. **未确认项与扫描限制**（表格，单条目一句话）：列出是否读取测试文件/配置模板/第三方依赖内部实现、`unconfirmed`/`inferred` 结论及其回溯或反向校验结果、项目类型识别置信度是否触发询问。

**不再单独设置"分页面数据流转图""核心数据流 sequenceDiagram""交互链路表""修改历史大列表"章节**——这些信息已经通过关系图的边标注（接口路径/函数名）和节点变更日志覆盖，重复维护两份会产生冗余和不一致风险。若某条端到端链路确实复杂到一张关系图无法表达分支细节（如一次下单涉及事务内 5 个以上步骤），可在该链路的核心节点变更日志下方追加一个 `[[...]]` 形状的"补充说明"节点，而不是另起一张 sequenceDiagram。

**文档体量超限自动拆分（项目级）**：当主文档关系图节点数超过约 25 个且无法通过「3. 用户关系图节点数超限拆分」规则在同一标题下容纳时，按业务域拆分到 `docs/cloud-map/<域名>.md`，主文档保留每个域一句话摘要 + 跳转链接；域子文档格式与主文档一致（4 节结构）。

Mermaid 节点 ID 应稳定简短（建议用页面/文件缩写+序号，如 `P10`、`F_createOrder`），便于后续增量更新时精确定位。只绘制有代码证据的关系，推测关系按置信度标签明确标注。

## 代码变更前确认

如果用户同时要求新增或修改业务代码，先完成云图（含变更日志条目的追加），然后只列候选方案并等待确认，不得修改业务代码：

| 候选节点 | 文件/符号 | 拟变更内容 | 变更类型 | 影响范围 |
|---|---|---|---|---|
| 关系图中的节点名 | 文件路径或函数名 | 具体新增/修改/删除 | 新增/变更/修复/重构/移除 | API、状态、测试、部署等 |

明确说明："以上仅为候选变更，尚未修改业务代码。请确认要执行的范围；收到明确确认后才会改代码，并在确认后把本次变更追加到云图对应节点的变更日志中。"确认前不得使用会改变业务代码的工具。

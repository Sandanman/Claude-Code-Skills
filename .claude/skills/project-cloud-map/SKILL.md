# Project/File Cloud Map

## 版本历史

- **v2.2**：将工作流重构为 `scope + operation` 两个维度，补充新增需求、目标文档状态、主图—子项映射、代码/业务双置信度、Fast/Durable Path、执行摘要和 Mermaid 分级校验规则。
- **v2.1**：新增已有云图补充模式：详细子项优先在主文件关系图中添加或修改，`<被分析目录>/cloud-map/` 仅作为必要兜底位置。
- **v2.0**：围绕查上下文和留痕场景，统一项目级/文件级云图、节点变更日志、关系图增量更新和体量拆分规则。
- **v1.0**：初始版本。

## 1. 核心定位与边界

读取当前代码快照，生成可审阅的 Markdown + Mermaid 云图，服务于：

1. **查上下文**：定位页面、路由、服务入口、文件或符号及其上下游关系。
2. **留痕**：在对应节点追加变更记录，保留历史轨迹。

### 1.1 分析对象

允许读取源码、路由、入口、接口定义、必要配置、已有云图文档和当前分支名称。禁止读取或推断 Git commit、diff、tag、blame、提交时间等历史信息；当前分支名仅用于变更日志。

禁止修改业务代码、业务配置、测试代码和部署配置。`project-cloud-map` 允许创建或增量更新用户明确要求维护的云图文档，但文档写入仍须遵循基线读取、确认节点和结果校验。

### 1.2 操作边界

- **分析阶段**：只读，形成证据、候选位置和影响范围。
- **云图写入阶段**：仅写目标云图文档，不修改业务代码。
- **业务代码阶段**：本 Skill 不执行；涉及业务代码时只输出候选变更表，等待用户明确确认后交由其他 Skill 处理。
- **只读分析请求**：用户使用“分析、查看、解释、定位、评估”且未要求保存时，不创建或修改云图文件。

## 2. 工作模型

先识别 `scope`，再识别 `operation`。两者是独立维度，不互相替代。

### 2.1 scope

| scope | 含义 | 默认范围 |
| --- | --- | --- |
| `project` | 项目级云图 | 页面、路由、服务入口、命令、公共导出和业务域 |
| `map-supplement` | 以已有项目云图为上下文的补充 | 主文件关系图及目标业务域相关子项 |
| `file` | 文件级云图 | 指定文件的函数、方法、类及直接依赖/调用边界 |

### 2.2 operation

| operation | 含义 | 是否默认写入 |
| --- | --- | --- |
| `generate` | 首次生成云图 | 是，目标明确且无确认阻塞时 |
| `supplement` | 新增模块、细化已有节点或补充业务子项 | 是，位置明确且无确认阻塞时 |
| `record-change` | 仅向已有节点追加变更日志 | 是，节点明确时 |
| `analyze` | 只分析现状、候选位置或影响范围 | 否 |

常见组合包括 `project + generate`、`map-supplement + supplement`、`project + record-change` 和 `file + analyze`。

### 2.3 输出路径

云图生成到被分析的目录下：分析整个项目时 `<被分析目录>` 为项目根目录，分析某子目录时为该子目录；文件级云图写在被分析文件所在目录。

- 项目级主文件：优先 `<被分析目录>/project-cloud-map.md`。
- 项目级拆分子文档：只有主文件整体无法承载、已有独立子文档必须延续或用户明确指定时才使用 `<被分析目录>/cloud-map/<域名>.md`。
- 文件级文档：`<被分析文件所在目录>/<文件名>.cloud-map.md`。

文件级输出属于用户明确指定的文件范围，不等同于项目级补充；若其业务域已有主图，应读取主图相关节点作为上下文。

## 3. Orchestrator 路径与确认原则

### 3.1 Fast Path

仅在以下条件同时满足时使用 Fast Path：单一 scope、单一 operation、目标明确、主图与子文档无冲突、业务归属无歧义、无需用户确认、不涉及业务代码修改，且属于低风险云图文档写入或只读分析。

```text
意图识别 → scope/operation 判定 → 读取基线 → 分析/写入 → L0 校验 → 输出摘要
```

### 3.2 Durable Path

以下任一情况必须进入或升级到 Durable Path：新增需求、多个候选归属、主图与子文档冲突、主文件缺失但有子文档、项目类型不明确、跨文档同步、低置信度、需要暂停/恢复/重试、Mermaid 校验失败后修复、用户要求业务代码变更或需要完整审计记录。

Durable Path 至少记录：任务 ID、scope、operation、读取范围、目标文档状态、候选位置、确认状态、子项映射、校验级别、失败/暂停原因和最终状态。按 Orchestrator 规则执行 L1 校验，只有失败、高风险或用户要求时触发 L2。

### 3.3 确认节点

1. **归属确认**：多个业务域、入口或主图节点均可能匹配时暂停写入。
2. **拆分确认**：主文件无法承载且存在多种拆分方案时列出方案并暂停。
3. **代码变更确认**：涉及业务代码时只输出候选变更表，不修改业务代码。

## 4. 统一执行流程

1. **识别意图**：提取 `scope`、`operation`、目标、业务上下文、关键词、成功标准和是否需要确认。
2. **检查目标文档**：判断主文件、域子文档和文件级文档是否存在、可解析及是否互相冲突。
3. **确定读取范围**：读取源码、入口、路由、配置和相关云图；记录排除项。默认排除 `node_modules`、构建产物、历史目录和测试文件，并说明原因。
4. **收集证据**：追踪触发者/调用者 → 节点逻辑 → 下游节点 → 数据访问/外部系统 → 返回/副作用，记录权限、异步、错误和共享状态。
5. **定位或建模**：定位现有节点，或确定新增节点、subgraph 和真实调用边；不得用猜测替代代码证据。
6. **判断确认**：存在归属、拆分、冲突或代码变更确认节点时暂停，并输出候选位置、证据和影响范围。
7. **增量写入或只读输出**：确认通过后只更新目标云图；`analyze` 仅输出分析，不写文件。
8. **执行校验**：按 L0/L1/L2 检查 Mermaid 结构、语义、映射和反向关系。
9. **输出摘要**：输出 Orchestrator 所需可观测字段和未完成项；未通过校验不得报告“已完成”。

## 5. 目标文档状态处理

| 状态 | 处理方式 |
| --- | --- |
| 主文件存在且可解析 | 完整读取主文件作为基线，禁止整体覆盖重写 |
| 主文件不存在且无子文档 | 按首次生成创建 `<被分析目录>/project-cloud-map.md` |
| 主文件不存在但存在子文档 | 先读取子文档，保留其历史；主文件补充摘要/索引需进入 Durable Path |
| 主文件为空或结构损坏 | 不直接覆盖，输出修复候选并请求确认 |
| 主文件与子文档冲突 | 以当前代码证据为准，记录冲突并请求确认 |
| 用户明确指定子文档 | 可维护指定文档，但检查主文件是否需要同步摘要、节点或索引 |
| 用户只要求分析 | 不创建、不修改任何云图文件 |

主文件不存在不是自动切换到 `<被分析目录>/cloud-map/` 的理由。主文件优先原则始终有效。

## 6. 云图操作流程

### 6.1 首次生成

1. 判断项目类型 Web、全栈、后端、CLI 或库，并记录代码证据；证据不足时列候选并请求确认。
2. 项目级按页面/路由/服务入口/业务域建模；文件级按函数/方法/类建模。
3. 使用 subgraph 按业务域或分层组织节点，边上标注真实接口路径、函数名或调用符号。
4. 为每个节点创建稳定 ID，并写入首条 `新增` 变更日志。
5. 输出文件索引和未确认项。

### 6.2 新增需求

1. 从需求提取功能、业务域、入口、上游、下游和可能文件范围。
2. 在主图中查找强关联节点并执行一次反向校验。
3. 有明确调用关系时接入真实调用链；只有业务语义关联时不得自动接边；完全无关联时建立独立节点或 subgraph。
4. 为新节点分配稳定 ID，补充入口、业务处理、关键分支、权限、数据访问、异常路径和返回/副作用等详细子项。
5. 新节点追加首条 `日期 分支 新增: 功能描述` 日志。
6. 存在多个合理位置时先列候选，不写入。

### 6.3 已有云图补充

1. 完整读取 `<被分析目录>/project-cloud-map.md` 的关系图，再读取目标业务域相关子文档。
2. 依据业务上下文和代码证据定位业务域、入口、上游和下游。
3. 详细子项优先直接添加到主文件关系图对应的 subgraph 或节点附近，不得仅新建 `<被分析目录>/cloud-map/` 代替主图更新。
4. 已有语义相同的节点、边或子项直接补充/修改，复用稳定 ID，不重复创建，不删除历史节点、边或日志。
5. 新增关系必须接入真实调用链；仅业务关联的关系标记为 `inferred` 或 `unconfirmed`，不得臆造调用。
6. 同步主图、文件/符号索引、子项映射和变更日志。

### 6.4 变更需求与节点移除

1. 优先按文件路径、函数名、类名或路由路径精确定位既有节点。
2. 只追加变更日志，不因标签变化重建节点；没有日志时创建补记条目。
3. 新增/移除边时同步更新关系图并记录原因。
4. 节点整体移除时保留节点和历史日志，追加 `移除`，可标记“已废弃”，不得直接消失。
5. 修复和重构分别使用 `修复`、`重构`。

## 7. 主图—详细子项映射

详细子项优先放在主文件关系图中。每个子项必须可追溯到以下字段：

| 字段 | 要求 |
| --- | --- |
| `node_id` | 主图中的稳定节点 ID |
| `parent_id` | 所属主节点或业务域 |
| `symbol` | 文件、函数、方法、类或路由 |
| `evidence` | 代码证据位置 |
| `code_confidence` | 代码证据置信度 |
| `business_confidence` | 业务上下文置信度 |
| `change_log_ref` | 对应变更日志子节点 |
| `source_doc` | 主文件或子文档路径 |

详细子项最小结构为：入口/触发、参数或状态、业务处理、关键分支、权限判断、数据访问/外部集成、异常路径、返回/副作用和变更日志。子项 ID 可使用主节点 ID 作为前缀。子文档中的 ID 必须与主图一致，或明确声明别名关系。

主图不能只保留“详见子文档”；使用子文档时必须保留摘要、主图节点、索引或映射。

## 8. 置信度与证据

### 8.1 代码证据置信度

- `confirmed`：直接读到定义与调用，或数据读写双方。
- `inferred`：有局部代码证据，但调用链不完整，已完成一次反向校验。
- `unconfirmed`：完成最低回溯仍无代码证据。

判定 `unconfirmed` 前检查：生命周期钩子/入口、参数/props/上下文订阅、同域相似节点模式。

### 8.2 业务上下文置信度

- `confirmed`：用户明确说明，或已有云图与代码语义一致。
- `inferred`：根据命名、目录、路由或相邻模块推断。
- `unconfirmed`：无法确认业务归属或用户意图。

代码证据 confirmed 不代表业务归属 confirmed；业务上下文 confirmed 也不允许臆造代码调用边。任一维度不确定时必须输出对应不确定项。

## 9. 拆分与 cloud-map 子文档使用规则

先在主文件“关系图”章节内拆分多张 Mermaid 图，再评估是否建立子文档。满足任一条件时进入拆分评估：

- 单张图节点超过 25 个；
- 边数超过节点数的 2.5 倍；
- 单一 subgraph 超过 12 个节点；
- 同图包含超过 3 个业务域；
- 标签、日志或证据导致图不可审阅。

拆分优先级：业务域 → 分层 → 入口链路。不得通过“若干页面”等概括节点规避拆分。只有主文件整体无法承载、已有独立子文档必须保持历史连续性或用户明确指定时，才使用 `<被分析目录>/cloud-map/`。拆分后主文件必须保留摘要、入口节点、路径索引和 ID 映射。

## 10. 输出格式与执行摘要

每份云图文档包含：

1. **范围与模式**：`scope`、`operation`、读取范围和排除项。
2. **关系图**：Mermaid flowchart，按业务域/层级组织，边标注真实依据，非 confirmed 关系标记置信度。
3. **文件/符号索引**：关键文件、路由、函数、方法、类和节点 ID。
4. **未确认项与扫描限制**：代码/业务双置信度、反向校验结果和排除范围。

执行结果兼容 Orchestrator 固定摘要：

```text
主 Skill：project-cloud-map
匹配关键词：{matched_keywords}
匹配分数：{match_score}
选择理由：{selection_reason}
声明依赖：[]
执行路径：fast / durable
scope：project / map-supplement / file
operation：generate / supplement / record-change / analyze
是否持久化：{persisted}
任务 ID：{task_id 或 N/A}
目标文档状态：{状态}
主文件优先决策：{说明}
候选确认状态：{无需确认 / 待确认 / 已确认}
校验级别：L0 / L1 / L2
代码置信度：{confirmed / inferred / unconfirmed}
业务上下文置信度：{confirmed / inferred / unconfirmed}
状态：已完成 / 部分完成 / 待确认 / 失败
未完成项：{无或具体事项}
```

仅完成扫描未写入、候选未确认、映射未校验或 Mermaid 失败时，不得报告“已完成”。

## 11. Mermaid 分级校验

### L0：结构校验

- Mermaid fenced block 和 `flowchart` 声明存在且闭合。
- 节点 ID 非空、稳定且唯一。
- subgraph 成对闭合，边引用的节点存在。
- 权限节点使用统一菱形，日志节点使用 `[[...]]`。

### L1：语义校验

- 关键边有真实接口、函数名或调用符号。
- 非 confirmed 节点和边带有置信度。
- 节点与文件/符号索引可互相追溯。
- 主图与详细子项的 ID、业务域和日志映射一致。
- 拆分子文档在主图中有摘要或索引。
- 没有重复语义节点和重复边。

### L2：反向校验

L1 失败、高风险、主子图冲突或用户明确要求时触发：从下游反查上游、从数据模型反查写入来源、从路由反查入口、从主图反查文件/符号、从子项反查主图 ID。

## 12. 业务代码变更前确认

如果用户同时要求新增或修改业务代码，先完成云图分析并列出候选方案，不得修改业务代码：

| 候选节点 | 文件/符号 | 拟变更内容 | 变更类型 | 影响范围 |
| --- | --- | --- | --- | --- |
| 关系图中的节点名 | 文件路径或函数名 | 具体新增/修改/删除 | 新增/变更/修复/重构/移除 | API、状态、测试、部署等 |

必须明确：以上仅为候选变更，尚未修改业务代码；收到明确确认后才会执行代码修改，并在完成后将事实性变更追加到对应节点日志。

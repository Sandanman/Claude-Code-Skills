# Skill Analyzer v1.0

## 概述

本 Skill 用于系统化地解读和分析任意 Skill 的 SKILL.md 文件，生成结构化的分析报告。

输入：一个 Skill 的路径（`.claude/skills/<skill-name>/SKILL.md`）
输出：一份完整的能力分析文档（Markdown 格式）

## 分析维度

本 Skill 按以下 8 个维度系统化解读 Skill：

| 维度 | 编号 | 说明 |
|------|------|------|
| 功能说明 | 1 | Skill 做什么，解决什么问题 |
| 执行流程 | 2 | 执行管道、原子技能依赖关系 |
| 最终输出 | 3 | Skill 的输出产物和格式 |
| 架构设计 | 4 | 架构模式、设计原则 |
| 思维方式 | 5 | 设计者背后的问题解决思路 |
| 这样做的好处 | 6 | 相对于替代方案的优势 |
| 优缺点分析 | 7 | 平衡的利弊评估 |
| 使用建议 | 8 | 最佳实践和注意事项 |

## 执行流程

### 第一步：读取目标 Skill 文件

读取用户提供的 Skill 的 `SKILL.md`，如果存在以下文件也一并读取：
- `atomic-skills/*/SKILL.md`（原子技能详情）
- `README.md`（使用说明）
- `config.md`（配置文件）
- `technical_implementation.md`（技术实现细节）

### 第二步：解析结构

从 SKILL.md 中提取：

**Frontmatter 信息**：
- `name`：技能名称
- `description`：触发描述
- 版本号（从正文中查找）

**结构信息**：
- 执行流程图/ASCII 图（如果有）
- 原子技能列表
- 核心能力列表
- 完成标准
- τ 增强字段（如果有）

### 第三步：功能分析

回答以下问题：
1. **这个 Skill 的核心功能是什么？**（1 句话 + 3-5 句详细说明）
2. **它解决什么问题？** 什么场景下会用到它？
3. **它的触发条件是什么？** 用户说什么时会调用它？
4. **它有哪些子能力/原子技能？** 各负责什么？

### 第四步：执行流程分析

1. **提取执行管道**：从正文中找到执行流程描述，识别串行步骤和并行步骤
2. **分析依赖关系**：哪些步骤必须在前置步骤之后执行？哪些可以并行？
3. **识别关键节点**：哪些步骤是核心/不可折叠的？
4. **τ 控制机制**（如果有）：预算分配、折叠触发条件、借位策略

### 第五步：输出结果分析

1. **产出什么**：文件？文档？代码？命令？JSON？
2. **输出格式**：Markdown？代码块？特定文件类型？
3. **输出位置**：保存到哪个目录？哪个文件？

### 第六步：架构设计解读

分析并推断设计者的架构决策：

1. **架构模式**：
   - 管道模式（Pipe-and-Filter）？
   - 分层模式（Layered）？
   - 插件模式（Plugin）？
   - 模块化模式（Modular）？
   - τ 增强模式？

2. **设计原则**：
   - 单一职责（每个原子技能只做一件事）？
   - 可复用性（原子技能可被其他 Skill 调用）？
   - 可测试性（步骤解耦可独立验证）？
   - 渐进式披露（复杂信息分层加载）？

3. **τ 增强设计**（如果适用）：
   - Task Folding：哪些步骤被折叠？为什么？
   - Skill Stacking：上下文共享机制是什么？
   - Co-Design：Model×Rules×Skills 如何分配？
   - Pattern Mining：复用了哪些成熟模式？

### 第七步：思维方式推断

从架构和实现中推断设计者的思维方式：

1. **问题分解策略**：复杂问题是如何拆分的？按功能？按阶段？按复杂度？
2. **抽象层次**：设计者如何在具体实现和抽象概念之间平衡？
3. **权衡取舍**：设计者优先考虑了哪些因素？（性能？可维护性？易用性？）
4. **演进路径**：这个 Skill 是如何从简单到复杂演进的？（从版本历史推断）

### 第八步：优势分析

回答"这个设计为什么有效"：

1. **相对于无 Skill**：没有这个 Skill 时，用户需要做什么？
2. **相对于粗粒度设计**：拆成多个原子技能比单个大 Skill 好在哪里？
3. **相对于手工操作**：自动化带来哪些确定性和效率提升？
4. **τ 优化的价值**：τ 控制带来了哪些具体的节省？

### 第九步：优缺点平衡评估

| 维度 | 优点 | 缺点/限制 |
|------|------|---------|
| 可维护性 | 原子技能解耦，修改一个不影响其他 | 需要维护注册表和依赖关系 |
| 可扩展性 | 新增原子技能只需注册 | 架构变更可能影响已有链路 |
| 性能 | τ 控制避免过度消耗 | 折叠操作有决策开销 |
| 易用性 | 触发自动化，用户只需说需求 | 调试需要理解 Skill 间依赖 |
| 灵活性 | 多场景路由适应不同需求 | 场景边界不清时可能路由错误 |

### 第十步：生成报告并保存到文件

按上述模板生成完整的 Markdown 报告，然后**立即使用 Write 工具保存到文件**：

```
Write 工具路径：.claude/skills/skill-analyzer/skill-analyzer-reports/skill_analysis_<skill-name>.md
内容：完整报告（全部 8 个维度）
时间戳：使用 date 命令获取实际当前时间（如 2026-06-05 15:00:00），禁止硬编码
```

**执行顺序（严格遵守）**：
1. 生成报告 Markdown 内容
2. Write 工具写入文件 ✅ **文件写入必须先于对话输出**
3. 读取刚保存的文件（确认写入成功）
4. 在对话中输出精简版（保留 8 维度，用表格压缩）

## 执行规范（必须遵守）

1. **时间戳动态获取（MUST）**：文件顶部元数据和底部时间戳均使用 `date` 命令获取实际当前时间，禁止硬编码
2. **文件路径（固定）**：`.claude/skills/skill-analyzer/skill-analyzer-reports/skill_analysis_<skill-name>.md`
3. **对话输出（最后）**：文件写入成功后，在对话中输出精简版报告

## 使用说明

1. **用户输入示例**：
   - "解读一下 bug-solver 这个 Skill"
   - "帮我分析 .claude/skills/code-generator/SKILL.md"
   - "orchestrator-pro 的架构是什么样的？"

2. **Skill 路径推断**：如果用户只给了 Skill 名称，自动拼接为 `.claude/skills/<skill-name>/SKILL.md`

3. **灵活性**：对于不同复杂度的 Skill，分析深度可以调整——简单的 Skill 可以精简某些维度，复杂的 Skill（如 orchestrator-pro）应该详细分析每个原子技能

4. **精简输出**：对话中输出精简版报告（保留全部 8 个维度，用表格替代冗长描述），完整版保存到文件

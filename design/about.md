# 项目设计说明

## 当前有效架构

项目采用统一 `orchestrator` 作为任务入口。用户请求经过意图识别和 Skill 匹配后，生成由依赖关系组成的 DAG，并按执行层组织主 Skill 与原子 Skill。

通用流程如下：

```text
用户请求
  → 意图识别与复杂度评估
  → Skill 匹配
  → DAG 任务规划
  → 当前任务初始化
  → 按依赖执行并更新共享上下文
  → 结果校验
  → 输出执行结果
  → 任务归档
```

## 主要职责

| 组件 | 职责 |
|------|------|
| `orchestrator` | 统一入口、意图识别、Skill 匹配、DAG 规划、执行控制、校验和归档 |
| 主 Skill | 负责一个业务领域的专业处理，并组织本领域原子 Skill |
| 原子 Skill | 执行单一、可验证的具体步骤 |
| `task_skill.md` | 保存当前任务状态、执行日记和共享上下文 |
| 任务归档 | 将已完成任务移动到按月组织的历史目录，并更新索引 |

## DAG 与共享上下文

DAG 用于表达 Skill 之间的依赖关系。没有依赖的节点可以并行执行；依赖节点在上游完成后执行。每个节点应声明输入、输出和完成标准，执行状态实时写入当前任务文件。

上游节点生成的中间结果写入 `task_skill.md` 共享上下文，下游节点优先读取已确认的共享结果；共享结果不可用时，再按 Skill 声明读取项目文件或其他输入。这种方式减少重复分析，并保持跨 Skill 的数据契约清晰。

## 校验与归档

任务完成前需要同时检查：

1. 每个已选 Skill 是否满足自身完成标准
2. 所有依赖节点是否完成或被安全处理
3. 最终结果是否满足用户目标
4. 输出文件和状态记录是否完整

校验通过后，`orchestrator` 输出执行摘要和业务结果，并将当前任务归档到 `.claude/skills/tasks/history/YYYY-MM/`。无法完成的任务也应保留状态、失败原因、已完成部分和后续建议。

## 设计原则

- 所有任务统一从 `orchestrator` 进入，避免多套入口产生流程分歧
- 通过 DAG 表达依赖，按需并行，不预设固定线性流水线
- 通过共享上下文传递中间结果，避免跨 Skill 重复读取和解析
- 通过显式完成标准和结果校验控制输出质量
- 通过任务文件和月度归档保留可恢复、可追溯的执行记录
- 对缺失能力采用可解释、可控的降级处理，不执行未经授权的破坏性操作

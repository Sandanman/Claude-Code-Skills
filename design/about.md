# Claude Code Skills 架构设计总结

> 本文汇总了关于 Skill 编排系统设计的核心结论，涵盖混合架构、三层职责分工、SKILL.md 双模式与缺失处理机制。
> 
> 理论基础：华为韬定律（τ-Law）— 以 τ（时间常数）为核心性能指标，通过时间缩微而非堆模型参数提升 Agent 综合表现。
> 
> 准则依据：提升质量、缩短时耗、减少 Token。

---

## 一、混合架构：按复杂度分流

### 1.1 核心原则

**当任务为简单任务时，则只通过匹配到主 skill 直接执行任务。**

架构从"单一模式"变为**按复杂度分流的混合模式** — 简单任务让主 skill 直接执行（τ 开销最低），复杂任务才走编排层统一编排（解锁全局优化）。

三层结构定位：

| 层级 | 角色 | 类比 |
|------|------|------|
| **编排 skill**（orchestrator-pro） | "调度总控" — 决定做什么、用谁做、按什么顺序做、预算多少 | 工厂的生产调度中心 |
| **主 skill**（code-generator 等） | "业务专家" — 决定这件事怎么做才专业 | 工厂里的某条专业产线 |
| **原子 skill** | "最小执行单元" — 完成具体一步操作 | 产线上的单个工位 |

编排 skill 和主 skill 都是"编排器"，**结构同构、作用域不同** — 编排 skill 是全局编排器（跨领域，选主skill→编主skill→出全局报告），主 skill 是领域编排器（单领域内，选原子skill→编原子skill→出业务结果）。这是分形架构，每一层都是上一层的缩小版编排器。

### 1.2 两条路径

**路径 A：简单任务（complexity < 4）— 主 skill 直接执行**

```
用户输入
   ↓
[编排 skill]
   ├─ 意图识别 + 复杂度评分
   ├─ 匹配【单个】主 skill
   └─ 委托主 skill 全权处理 → 【end】
        ↓
   [主 skill]（完整领域编排器）
      ├─ 选择原子 skill 子集
      ├─ 编排 DAG（并行/串行）
      ├─ 执行原子 skill
      └─ 汇总业务结果 → 返回编排层
```

**特点**：编排层只做"匹配 + 委托"，**不参与执行**。主 skill 自己完成"选+编+执行+汇总"全链路。

**路径 A 下三层的功能明细**：

| 层级 | 在路径 A 中的功能 |
|------|-----------------|
| **编排 skill**（极轻） | ① 意图识别与复杂度评分（判定 < 4 走轻量路径）<br>② 从 `skills_register.md` 按关键词/语义匹配**单个**主 skill<br>③ 无匹配 → 记录 missing_skills.md + 自主兜底；多匹配 → 用户选择<br>④ 委托主 skill 全权处理，**不读取其 SKILL.md、不参与执行编排**<br>⑤ 接收主 skill 返回的业务结果，输出给用户 |
| **主 skill**（完整领域编排器，三动作全做） | **选择**：从自己的原子 skill 池中按任务特征动态选择相关子集（非全跑），选择逻辑是领域知识，编排层不干预<br>**编排**：构建原子 skill 间的 DAG（依赖关系），识别并行层（可委托 subagent），串行链路贯穿数据流（上游输出→下游输入）；在自己 τ 子预算内分项分配；领域内错误处理（重试/降级/跳过）<br>**汇总**：把各原子 skill 的片段输出聚合成领域业务结果（产出物清单 + 质量评估 + 后续建议），**是业务结果的唯一产出方** |
| **原子 skill**（单步执行） | 完成单一职责的一步操作（如 tech-stack-detection 只做技术栈检测）；无业务流程编排能力；由**主 skill 直接调度**；执行结果写入 task_skill.md 共享上下文供下游读取 |

**路径 A 的契约使用**：
- 编排层只读 `skills_register.md`（匹配主 skill），**不读**主 skill 的 SKILL.md
- 主 skill 读自己的 SKILL.md（第 4 章"简单任务执行流程"）+ task_skill.md（读写共享上下文区域）
- task_skill.md 用**简化版**（主 skill 级状态，不细化到原子 skill 状态）

**路径 B：复杂任务（complexity ≥ 4）— 编排层统一编排**

```
用户输入
   ↓
[编排 skill]
   ├─ 意图识别 + 复杂度评分
   ├─ 匹配【多个】主 skill 组合
   ├─ 读取各主 skill 的声明（原子skill池 + 选择规则 + DAG）
   ├─ 合并【全局 DAG】（跨主skill优化并行层）
   ├─ 统一执行原子 skill（τ监控 / Task Folding / Pattern Mining）
   ├─ 委托各主 skill 汇总各自业务结果
   └─ 输出全局报告 + 业务汇总
```

**特点**：主 skill 降为"声明 + 汇总"，编排层统一编排执行，解锁跨主 skill 全局优化。

**路径 B 下三层的功能明细**：

| 层级 | 在路径 B 中的功能 |
|------|-----------------|
| **编排 skill**（重职责，三动作全做） | **选择**：从 `skills_register.md` 匹配**多个**主 skill 组合；无匹配 → 记录 missing_skills.md + 自主兜底；多匹配 → 用户选择<br>**编排**：读取各主 skill 的 SKILL.md 声明（原子skill池 + 选择规则 + DAG），按选择规则确定要跑的原子 skill 子集，**合并为全局 DAG**（跨主skill边界优化并行层）；全局预算分配（τ/Token/Duration 三指标初始化与监控）；跨层优化（Task Folding 折叠冗余链路、Pattern Mining 历史复用、Skill Stacking 共享上下文）；task_skill.md 生命周期管理（实例化/实时写入/归档）<br>**汇总**：全局三指标报告（τ/Token/Duration 分解 + 异常标记）+ 任务归档索引 + 效率评分 + Co-Design 贡献度，**不汇总业务内容** |
| **主 skill**（降为"声明 + 汇总器"） | **声明**（非运行时编排）：在 SKILL.md 中提供原子 skill 池（候选集）+ 选择规则（任务特征→子集）+ 依赖关系 DAG + 汇总模板<br>**不再做**：不运行时选原子 skill、不编排 DAG、不执行原子 skill（这些由编排层代为执行）<br>**汇总**（保留）：执行完毕后，被编排层委托，把所属原子 skill 的片段输出聚合成**领域业务结果**（产出物清单 + 质量评估 + 后续建议），**仍是业务结果的唯一产出方** |
| **原子 skill**（单步执行） | 完成单一职责的一步操作（同路径 A）；无业务流程编排能力；由**编排层直接调度**（跨主 skill 边界）；执行结果写入 task_skill.md 共享上下文，供其他主 skill 的下游原子 skill 读取（Skill Stacking） |

**路径 B 的契约使用**：
- 编排层读 `skills_register.md`（匹配主 skill 组合）+ **读各主 skill 的 SKILL.md**（加载声明：原子skill池/选择规则/DAG）+ task_skill.md（管理生命周期）
- 主 skill 只读自己的 SKILL.md（第 1-3 章声明 + 第 5 章汇总模板）+ task_skill.md（读共享上下文做汇总）
- task_skill.md 用**完整版**（原子 skill 级状态，支持跨主 skill 的 Skill Stacking）

**路径 B 的关键变化**：
- 原子 skill 的调度方从"主 skill"变为"编排层" → 解锁跨主 skill 的全局 DAG 优化
- 主 skill 的选择规则所有权仍在自己（SKILL.md 声明），**执行权移交给编排层** — 类似"主 skill 提供策略，编排层执行策略"
- 编排层能做**跨主 skill 的统一选择**（如发现两个主 skill 都要跑 tech-stack-detection，只跑一次共享结果）— 这是三层架构做不到的 Skill Stacking 升级

### 1.3 两种模式的职责对比

| | 简单任务（路径A） | 复杂任务（路径B） |
|---|---|---|
| 编排 skill 职责 | 匹配 + 委托（极轻） | 匹配 + 合并DAG + 统一执行 + 委托汇总（重） |
| 主 skill 职责 | 完整领域编排器（选+编+执行+汇总） | 仅声明 + 汇总 |
| 原子 skill 编排者 | 主 skill | 编排 skill |
| τ 预算分配 | 编排层 ~10%，主 skill ~90% | 编排层 ~40%，主 skill ~20%，原子 skill ~40% |
| task_skill.md 粒度 | 简化版（主skill级状态） | 完整版（原子skill级状态） |
| 跨主skill 优化 | 不需要（只有一个主skill） | 需要（全局 DAG 合并） |

### 1.4 科学性验证

- ✅ **符合 τ 优化目标**：简单任务 τ 预算本就小，直接委托主 skill，τ 留给真正执行。
- ✅ **落地 K1 Task Folding 精神**：简单任务本身就是"可折叠"的 — 整个编排链路折叠成"主 skill 单跑"。
- ✅ **与现有设计无缝衔接**：项目已有 `complexity < 4 走轻量路径` 的分流，此原则把它明确化。
- ✅ **按需付费**：简单任务不付"编排税"，复杂任务才付。

### 1.5 需要明确的四个边界

**边界 1：简单任务的 task_skill.md 简化**

简单任务不细化到原子 skill 状态，只记录主 skill 级：

```markdown
# 简单任务 task_skill.md
- 主skill：code-generator
- 状态：执行中 / 已完成
- 业务结果：{主skill汇总输出}
- τ消耗：{总τ}
```

**边界 2：简单任务的 τ 预算分配**

```
简单任务 τ 预算（simple=5000）
  ├─ 编排层（匹配+委托）：~500（10%）
  └─ 主 skill（选+编+执行+汇总）：~4500（90%）
```

**边界 3：简单任务的错误处理**

主 skill 自己处理领域内错误（重试/降级/跳过）。只有以下情况上报编排层：
- 主 skill 发现任务实际复杂度超预期 → 申请升级为复杂路径
- 主 skill 缺失必要上下文（如需要其他主 skill 的输出）→ 申请协调

**边界 4：动态升级机制**

简单任务执行中，主 skill 发现"这事不简单"时：

```
[主 skill 执行中] 
   ↓ 发现复杂度上升（如需求模糊 / 依赖其他领域）
   ↓ 触发升级判定：complexity_re-estimate ≥ 4
   ↓ 上报编排层
[编排层] 接管 → 切换为复杂路径 B（合并DAG + 统一执行）
```

避免"简单任务硬扛成复杂任务"导致的质量塌方。

### 1.6 主 Skill 的 SKILL.md 双模式支持

#### 1.6.1 为什么需要"双模式"

主 skill 在路径 A 和路径 B 中扮演的角色不同：

| 模式 | 主 skill 角色 | 谁来读 SKILL.md | 读它的目的 |
|------|-------------|---------------|-----------|
| **路径 A（简单任务）** | 完整领域编排器（自己选+编+执行+汇总） | 主 skill 自己 | 加载"简单任务执行流程"，自己照着跑 |
| **路径 B（复杂任务）** | 声明 + 汇总器（不执行，只提供规则和汇总） | 编排 skill | 加载"原子skill池/选择规则/DAG"，代为选择和编排 |

**核心矛盾**：两种模式需要的"指令"完全不同 — 路径 A 需要"怎么做"的执行指令，路径 B 需要"选哪些+怎么排"的声明规则。如果把两套指令拆成两个文件，主 skill 的领域知识就分散了，维护成本翻倍。

**解决方案**：**一份 SKILL.md 同时承载两种模式**，按章节划分用途，不同模式只读对应章节。领域知识集中、维护单点、按需取用。

#### 1.6.2 SKILL.md 的五个章节及具体内容

```markdown
## 1. 原子 skill 池（候选集）         ← 复杂任务用（编排层读取）
## 2. 选择规则（任务特征→子集）       ← 复杂任务用（编排层代为选择）
## 3. 依赖关系 DAG                    ← 复杂任务用（编排层合并全局DAG）
## 4. 简单任务执行流程                ← 简单任务用（主skill自己执行）
## 5. 汇总模板（业务结果输出格式）    ← 两种模式都用
```

**逐章详解**（以 code-generator 为例）：

**第 1 章 · 原子 skill 池（候选集）**

声明这个主 skill 拥有的全部原子 skill，**只是清单，不是执行顺序**。

```markdown
## 1. 原子 skill 池

| 原子 skill | 职责 | 输入 | 输出 |
|-----------|------|------|------|
| multi-scenario-adapter | 场景识别 | 用户输入 | 场景标签 |
| requirement-reader | 读取需求文档 | requirements.json | 结构化需求 |
| requirement-analysis | 分析自由文本需求 | 自由文本 | 结构化需求 |
| tech-stack-detection | 技术栈检测 | 项目目录 | 技术栈信息 |
| code-design | 代码结构设计 | 需求+技术栈 | 设计方案 |
| code-generation | 代码生成 | 设计方案 | 代码文件 |
| module-integration | 模块整合 | 多个代码文件 | 整合后代码 |
| code-validation | 代码验证 | 代码文件 | 验证报告 |
| documentation-update | 文档更新 | 代码+验证 | 文档变更 |
```

**用途**：路径 B 下，编排层读这一章，知道"code-generator 有哪些原子 skill 可选"。

**第 2 章 · 选择规则（任务特征→子集）**

声明"什么任务选哪些原子 skill"。**这是领域知识的核心**，编排层路径 B 下代为执行选择。

```markdown
## 2. 选择规则

| 任务特征 | 选择的原子 skill 子集 |
|---------|---------------------|
| 标准输入（有 requirements.json） | requirement-reader + tech-stack-detection + code-design + code-generation + code-validation + documentation-update |
| 简单需求（< 50字、1个功能点） | requirement-analysis + code-generation + code-validation |
| 复杂需求（> 100字、≥2功能点） | requirement-analysis + tech-stack-detection + code-design + code-generation + code-validation + documentation-update |
| 多模块（≥3模块） | requirement-analysis + tech-stack-detection + code-design + code-generation + module-integration + code-validation + documentation-update |
```

**用途**：路径 B 下，编排层根据任务特征匹配此表，确定要跑的原子 skill 子集。

**第 3 章 · 依赖关系 DAG**

声明原子 skill 间的依赖关系（有向无环图）。**编排层路径 B 下用这个合并全局 DAG**。

```markdown
## 3. 依赖关系 DAG

requirement-reader        → tech-stack-detection
requirement-analysis      → tech-stack-detection
tech-stack-detection      → code-design
code-design               → code-generation
code-generation           → module-integration
code-generation           → code-validation
module-integration        → code-validation
code-validation           → documentation-update

并行层识别：
  Layer 1: requirement-reader ∥ requirement-analysis（无依赖可并跑）
  Layer 2: tech-stack-detection
  Layer 3: code-design
  Layer 4: code-generation
  Layer 5: module-integration
  Layer 6: code-validation
  Layer 7: documentation-update
```

**用途**：路径 B 下，编排层把多个主 skill 的 DAG 合并为全局 DAG，识别跨主 skill 的并行机会。

**第 4 章 · 简单任务执行流程**

**只在路径 A 使用**。主 skill 自己执行时，按这一章的指令"怎么做"。这是主 skill 作为"完整领域编排器"的运行时逻辑。

```markdown
## 4. 简单任务执行流程

【路径 A 专用，主 skill 自己执行】

1. 读取 task_skill.md 共享上下文（如有）
2. 按第 2 章选择规则确定原子 skill 子集
3. 按第 3 章 DAG 构建执行顺序（并行层用 subagent，串行链贯穿数据流）
4. 逐层执行原子 skill：
   - 每个原子 skill 执行前：写入 task_skill.md 状态"执行中"
   - 执行后：写入状态"已完成"+ 共享上下文
   - 失败：领域内重试/降级/跳过（核心步骤不可跳过）
5. τ 子预算监控（超支时折叠可选步骤）
6. 全部完成后，按第 5 章汇总模板生成业务结果
7. 返回业务结果给编排层
```

**用途**：路径 A 下，主 skill 读这一章，照着一步步执行。编排层**不读这一章**（它不参与执行）。

**第 5 章 · 汇总模板（业务结果输出格式）**

**两种模式都用**。定义"业务结果长什么样"。

```markdown
## 5. 汇总模板

【两种模式都用，主 skill 汇总时套用】

### 产出物清单
- 生成的文件：{路径列表}
- 模块结构：{模块树}

### 质量评估
- 规范符合度：{✓/✗ + 说明}
- 验证结果：{通过/未通过 + 详情}

### 后续建议
- 待优化项：{列表}
- 建议的后续 skill：{如 code-optimizer / test-generator}
```

**用途**：
- 路径 A：主 skill 自己执行完后，套用此模板生成业务结果
- 路径 B：编排层执行完所有原子 skill 后，**委托主 skill** 套用此模板生成业务结果

#### 1.6.3 两种模式的"读取路径"

同一份 SKILL.md，两种模式读的章节不同：

```
路径 A（简单任务，主 skill 自己读）：
  读 第 2 章（选哪些）+ 第 3 章（怎么排）+ 第 4 章（怎么做）+ 第 5 章（怎么汇总）
  → 主 skill 照着自跑全链路

路径 B（复杂任务，编排层读）：
  读 第 1 章（有哪些）+ 第 2 章（选哪些）+ 第 3 章（怎么排）
  → 编排层代为选择+合并全局DAG+统一执行
  执行完后再委托主 skill 读 第 5 章（怎么汇总）生成业务结果
  → 主 skill 只参与"汇总"这一步
```

**章节与模式的对应关系**：

| 章节 | 路径 A（主 skill 读） | 路径 B（编排层 / 主 skill 读） |
|------|---------------------|----------------------------|
| 1. 原子 skill 池 | 不读（自己知道） | 编排层读 |
| 2. 选择规则 | 读（自己选） | 编排层读（代选） |
| 3. 依赖关系 DAG | 读（自己编） | 编排层读（合并全局DAG） |
| 4. 简单任务执行流程 | **读（核心）** | 不读 |
| 5. 汇总模板 | 读（自己汇总） | 主 skill 读（被委托汇总） |

#### 1.6.4 双模式的好处

1. **领域知识集中**：code-generator 的所有领域知识（有哪些原子skill、怎么选、怎么排、怎么执行、怎么汇总）都在一个文件里，维护单点。
2. **按需取用**：路径 A 只读"怎么做"，路径 B 只读"选哪些+怎么排"，互不干扰。
3. **解耦演进**：调整选择规则（第 2 章）或 DAG（第 3 章），不影响简单任务的执行流程（第 4 章）；反之亦然。
4. **契约清晰**：编排层和主 skill 的"接口"就是这份 SKILL.md，双方按章节约定读取范围，不会越界。

#### 1.6.5 反模式：写成固定线性流水线

**❌ 错误写法**（退化成流程引擎）：

```markdown
## code-generator 执行流程

步骤 1: 读取需求
步骤 2: 检测技术栈
步骤 3: 设计代码结构
步骤 4: 生成代码
步骤 5: 模块整合
步骤 6: 代码验证
步骤 7: 更新文档
```

**为什么错**：

| 问题 | 说明 |
|------|------|
| 丢失"动态选择" | 简单任务也被迫跑 7 步，τ 浪费在不必要步骤上（如简单函数不需要 module-integration）|
| 丢失"并行优化" | 强制线性，无法识别 requirement-reader 和 requirement-analysis 可并跑 |
| 无法支持路径 B | 编排层读不到"选择规则"和"DAG"，无法代为选择和合并全局 DAG |
| 退化成流程引擎 | 主 skill 变成"按步骤执行的脚本"，失去领域编排器的灵活性 |

**✅ 正确写法**：用第 1-3 章声明"有什么、选哪些、怎么排"，用第 4 章描述"简单任务怎么跑"，保持"动态选择"能力。

#### 1.6.6 一句话总结

**双模式的本质**：一份 SKILL.md = 一份领域知识包。第 1-3 章是"声明"（有什么/选哪些/怎么排，供编排层路径 B 读取），第 4 章是"执行指令"（供主 skill 路径 A 自跑），第 5 章是"汇总模板"（两种模式共用）。同一份文件，按模式取用不同章节，既保证领域知识集中维护，又支持两种执行路径的灵活切换。

### 1.7 功能边界红线

**编排 Skill 禁止越界**：

| 禁止行为 | 原因 |
|---------|------|
| 不选具体的原子 skill | 领域选择权属于主 skill |
| 不定义领域内的依赖关系 | DAG 由主 skill 定义 |
| 不汇总业务内容 | 业务汇总是主 skill 的职责 |
| 不硬编码领域质量标准 | 如"Vue 用 Composition API"是主 skill 的事 |
| 不跨过主 skill 直接编排原子 skill | 破坏分层（无匹配自主兜底除外）|

**主 Skill 禁止越界**：

| 禁止行为 | 原因 |
|---------|------|
| 不决定自己何时被触发 | 由编排层意图匹配决定 |
| 不管理全局 task_skill.md 生命周期 | 只读写共享上下文区域，不负责实例化/归档 |
| 不分配全局 τ 预算 | 只在自己子预算内再分配 |
| 不跨领域调度其他主 skill | 跨主 skill 协作由编排层编排 |
| 不输出全局三指标报告 | 只输出业务结果 |

### 1.8 契约接口（解耦点）

三个文件构成编排 skill 与主 skill 的**唯一契约**，解耦协作：

```
┌─ skills_register.md ──── 主 skill 元数据（name/path/keywords/ability）
│        ↑ 编排层读取用于匹配
│
├─ 主 skill 的 SKILL.md ── 原子skill池 + 选择规则 + DAG + 汇总模板
│        ↑ 编排层匹配后 Read 加载，主 skill 自身定义
│
└─ task_skill.md ──────── 运行时共享黑板
         编排层管理生命周期，主 skill 读写"共享上下文"区域
```

**解耦保证**：主 skill 修改自己的 SKILL.md（调整原子skill池/选择规则/DAG），不需要改编排层。

## 二、Skill 缺失的智驾雷达式自主探索

### 2.1 核心原则

**当 skill 缺失时，编排 skill 依照智驾雷达系统的逻辑自主探索实现，如果实在没有办法完成，则输出错误信息结论给用户。**

缺失不等于失败，先探索，实在不行才报错。这与 design.md 的"自主探索模式"和"skill 补充模式"完全对齐。

### 2.2 智驾雷达类比：四层处理模型

| 雷达系统 | Skill 系统映射 | 核心动作 |
|---------|---------------|---------|
| 感知层（雷达扫描） | 缺失检测 + 资源扫描 | 识别缺失的 skill 功能，扫描本地/网络可用资源 |
| 决策层（路径规划） | 替代方案探索 | 规划替代路径（组合现有 skill / subAgent 自主实现）|
| 执行层（自主行驶） | 自主尝试执行 | 用替代方案尝试完成任务 |
| 安全层（紧急制动） | 错误结论输出 | 实在无法完成 → 输出明确错误信息给用户 |

**核心理念**：雷达系统的目标不是"遇到障碍就停车"，而是"尽可能绕过障碍到达目的地，只有无路可走才停车"。

### 2.3 三层探索逻辑（由近及远）

**第一层：本地雷达扫描（感知替代资源）**

```
[缺失检测] 需要原子skill X，但池中没有
    ↓
[本地扫描]
   ├─ 在 .claude/skills/ 全目录搜索功能相近的 skill（可能未注册但存在）
   ├─ 检查是否有可组合的现有原子 skill 能替代 X 的功能
   └─ 检查 pattern 库是否有历史相似任务的执行模式可复用
    ↓
找到替代 → 用替代方案执行
未找到  → 进入第二层
```

**第二层：subAgent 近场探索（自主绕行）**

```
[启动 general-purpose subAgent]
   ├─ 传入：任务上下文 + 缺失skill的功能描述
   ├─ subAgent 自主分析：能否用基础工具（Read/Write/Bash/Grep等）完成该步骤
   ├─ subAgent 自主尝试实现缺失功能
   └─ 返回：成功结果 OR 探索失败报告
    ↓
成功 → 继续后续流程
失败 → 进入第三层
```

**关键**：subAgent 在独立上下文探索，不污染主流程的 τ 预算，失败也不影响主流程的状态。

**第三层：远场探索（网络 + 自主实现）**

```
[网络探索 + 自主实现]
   ├─ WebSearch 搜索相关方案/代码/文档
   ├─ 基于搜索结果，subAgent 自主实现缺失功能
   ├─ 验证实现质量（如能验证）
   └─ 返回：成功 OR 最终失败
    ↓
成功 → 执行 + 记录到 missing_skills.md（后续补充正式 skill）
失败 → 进入安全层
```

### 2.4 三道安全停止线

智驾系统有"安全边界"，skill 系统同样需要三道停止线，避免无限探索耗尽资源：

| 停止线 | 触发条件 | 动作 |
|--------|---------|------|
| τ 探索预算耗尽 | 探索消耗 τ 超过总预算 30% | 停止探索 → 进入安全层 |
| 置信度阈值 | 自主探索成功概率评估 < 0.5 | 停止探索 → 进入安全层 |
| 破坏性风险 | 涉及生产环境/不可逆操作/安全敏感 | 立即停止 → 进入安全层（不探索）|

**第三道线最重要**：涉及 `git push --force`、删除文件、生产部署等不可逆操作时，**不允许自主探索**，必须直接报错让用户决策。这是智驾系统的"绝对安全原则"。

### 2.5 简单任务 vs 复杂任务的缺失处理差异

**简单任务（原子 skill 缺失）**：

```
[主 skill 执行中] 发现原子skill X 缺失
    ↓
主 skill 自己尝试第一层（本地扫描，在自己的领域内）
    ↓ 找不到
上报编排层
    ↓
编排层启动第二层（subAgent 探索）
    ↓ 失败
编排层启动第三层（网络探索）
    ↓ 失败
→ 安全层：输出错误结论
```

**复杂任务（主 skill 缺失）**：

```
[编排层规划阶段] 发现需要主 skill Y，但未注册
    ↓
编排层直接启动三层探索（跳过主skill自探索，因为主skill本身缺失）
    ├─ 第一层：本地扫描是否有未注册的 skill 可用
    ├─ 第二层：subAgent 尝试用现有主 skill 组合替代
    └─ 第三层：subAgent 自主实现该领域逻辑
    ↓ 全部失败
→ 安全层：输出错误结论
```

### 2.6 错误信息输出规范（安全层）

错误信息不应该是简单的"任务失败"，而应该是**雷达系统的"事故报告"**，让用户清楚知道发生了什么、可以怎么做：

```markdown
## ⚠️ 任务无法完成 — 探索报告

### 缺失资源
- 缺失 skill：{skill名称}（{主skill/原子skill}）
- 功能描述：{该skill应承担的功能}
- 缺失位置：{在DAG中的位置/在执行流程的哪一步}

### 已尝试的探索路径
1. ✗ 本地扫描：未找到功能相近的替代 skill
2. ✗ subAgent 自主探索：{探索结果摘要}，置信度 0.3
3. ✗ 网络探索：{搜索结果摘要}，无可用方案

### 停止原因
- 触发停止线：{τ预算耗尽 / 置信度不足 / 破坏性风险}

### 给用户的建议
- 选项1：补充缺失的 skill（参考 missing_skills.md 的记录）
- 选项2：手动完成该步骤后重新发起任务
- 选项3：调整任务描述，规避该功能需求
- 选项4：如确需该能力，可创建 skill 后重试

### 部分成果（如有）
- 已完成的步骤：{列出已完成的部分}
- 可复用的中间产物：{文件/上下文}
```

**关键**：错误输出是**结论性的、可行动的**，不是模糊的"失败了"。

### 2.7 预判能力（雷达的前瞻扫描）

智驾雷达的精髓是**提前感知**，不是"撞上去了再绕"。映射到 skill 系统：

**编排阶段就预判缺失**：

```
[编排层规划阶段]
   ├─ 意图识别后，预判任务可能需要的 skill 集合
   ├─ 对比 skills_register.md，识别可能缺失的 skill
   ├─ 提前启动 subAgent 预探索（后台并行）   ← 关键
   └─ 规划工作流时，为可能缺失的节点预留"探索窗口"
```

**收益**：执行到缺失节点时，探索可能已完成，**零等待**。这正是 design.md 说的"减少工作流中的等待时间"。

**预探索的 subAgent 后台运行**：

```
编排层规划任务
    ↓
    ├─ 主流程：开始执行已确定的 skill
    └─ 后台 subAgent：并行预探索可能缺失的 skill  ← 同时进行
            ↓ 探索成功
        结果注入主流程的缺失节点
            ↓ 探索失败
        主流程到该节点时直接进入安全层（不重复探索）
```

### 2.8 与现有机制的整合

**missing_skills.md 的角色升级**：

从"缺失清单"升级为"**skill 演化的需求库**" — 每次探索失败都是一次需求收集，积累到一定程度可批量补充 skill。

```markdown
### {skill名称} - {缺失时间}
- 缺失类型：主skill / 原子skill
- 功能描述：{应承担的功能}
- 触发场景：{什么任务需要它}
- 已探索路径：{三层探索的记录}
- 探索失败原因：{为什么没成功}
- 建议补充方式：{基于探索经验给出的补充建议}
- 临时替代方案：{如果有 subAgent 自主实现的临时逻辑，记录下来}
```

**pattern 库的复用**：

探索成功后，把"自主探索的执行模式"存入 pattern 库。下次相似任务可直接复用探索结果，**不用重新探索**。这是 K4 Pattern Mining 在探索场景的应用。

### 2.9 设计要点

1. **探索预算独立分配**：探索消耗的 τ 从"探索专用预算"扣除，不吃主流程执行预算。
   ```
   任务总 τ 预算
     ├─ 主流程执行：70%
     └─ 探索储备：30%（仅在缺失时启用，不用则归还）
   ```
2. **探索的幂等性**：同一缺失节点的探索结果可缓存，不重复探索。探索失败也缓存"失败结论"，避免重试浪费。
3. **用户可见性**：探索过程对用户透明可见（流式输出），让用户知道"系统在努力找替代方案"，而不是"卡住了"。
4. **探索成功后的 skill 沉淀**：如果 subAgent 自主实现的逻辑被多次（如 ≥3 次）探索复用，应升级为正式的原子 skill，写入 .claude/skills/。这是系统的"自主进化"能力。

## 四、核心结论速查

### 4.1 三层定位

| 层级 | 角色 | 三动作 |
|------|------|--------|
| 编排 skill | 全局编排器 | 选主skill → 编主skill → 出全局报告 |
| 主 skill | 领域编排器 | 选原子skill → 编原子skill → 出业务结果 |
| 原子 skill | 最小执行单元 | 单步操作 |

### 4.2 架构原则

1. **分形同构**：编排 skill 和主 skill 结构同构（都是选择-编排-汇总），作用域不同（全局 vs 领域）。
2. **按复杂度分流**：简单任务主 skill 直接执行（τ 最低），复杂任务编排层统一编排（解锁全局优化）。
3. **主 skill 双模式**：简单任务作为完整领域编排器，复杂任务降为"声明+汇总器"。同一份 SKILL.md 承载两种模式。
4. **智驾雷达式缺失处理**：三层探索（本地扫描→subAgent→网络）+ 三道停止线 + 结论性错误报告。
5. **契约解耦**：三个文件（skills_register.md + SKILL.md + task_skill.md）构成编排层与主 skill 的唯一契约。

### 4.3 τ 优化要点

- 简单任务不付"编排税"，τ 留给真正执行。
- 复杂任务通过全局 DAG 合并 + Task Folding 跨主 skill 优化。
- 探索有独立预算（30%），不吃主流程执行预算。
- 预判缺失 + 后台预探索，实现零等待。

### 4.4 边界红线

- 编排 skill：不选具体原子skill、不定义领域DAG、不汇总业务内容、不硬编码领域知识。
- 主 skill：不决定自身触发、不管理全局生命周期、不分配全局预算、不跨领域调度。
- 自主探索：破坏性风险操作不允许探索，必须直接报错。

## 五、流程总结

> 以下提炼系统全链路的执行流程，按"入口分流 → 两条路径 → 缺失处理"顺序组织。

### 5.1 总体入口流程

1. 用户输入 → 编排 skill 接管
2. 意图识别 + 复杂度评分（complexity_score）
3. 路径分流：
   - complexity < 4 → 路径 A（委托主 skill）
   - complexity ≥ 4 → 路径 B（编排层统一编排）

### 5.2 路径 A：简单任务执行流程

1. 编排层从 `skills_register.md` 匹配**单个**主 skill
2. 无匹配 → 记 missing_skills.md + 自主兜底；多匹配 → 用户选择
3. 委托主 skill 全权处理（编排层不读 SKILL.md、不参与执行）
4. 主 skill 读自己 SKILL.md 的第 4 章"简单任务执行流程"
5. 主 skill 三动作自跑：
   - 选：按第 2 章选择规则确定原子 skill 子集
   - 编：按第 3 章 DAG 构建执行顺序（并行层用 subagent，串行贯穿数据流）
   - 执行+汇总：逐层执行原子 skill → 套第 5 章模板汇总业务结果
6. 主 skill 返回业务结果 → 编排层输出给用户
7. task_skill.md 用简化版（主 skill 级状态）

### 5.3 路径 B：复杂任务执行流程

1. 编排层从 `skills_register.md` 匹配**多个**主 skill 组合
2. 读取各主 skill 的 SKILL.md 声明（第 1-3 章：原子skill池/选择规则/DAG）
3. 按选择规则确定原子 skill 子集
4. 合并为**全局 DAG**（跨主skill边界优化并行层）
5. 全局 τ/Token/Duration 预算分配与监控
6. 统一执行原子 skill（Task Folding 折叠、Pattern Mining 复用、Skill Stacking 共享上下文）
7. 执行完毕 → 委托各主 skill 读第 5 章模板汇总各自业务结果
8. 编排层输出：全局三指标报告 + 各主 skill 业务汇总
9. task_skill.md 用完整版（原子 skill 级状态）+ 归档到 history/YYYY-MM/

### 5.4 简单→复杂动态升级流程

1. 主 skill 执行中发现复杂度上升（需求模糊/依赖其他领域）
2. 触发升级判定：complexity_re-estimate ≥ 4
3. 上报编排层 → 接管 → 切换为路径 B（合并 DAG + 统一执行）

### 5.5 SKILL.md 双模式读取流程

- 路径 A：主 skill 读第 2+3+4+5 章（自跑全链路）
- 路径 B：编排层读第 1+2+3 章（代选+合并DAG+统一执行），执行后委托主 skill 读第 5 章（汇总）

### 5.6 Skill 缺失三层探索流程

1. 检测到缺失（简单任务原子skill缺失 / 复杂任务主skill缺失）
2. 第一层·本地扫描：搜 `.claude/skills/` 相近 skill + 可组合替代 + pattern 库复用
3. 第二层·subAgent 近场探索：启动 general-purpose subAgent 用基础工具自主实现
4. 第三层·远场探索：WebSearch 搜方案 + subAgent 自主实现 + 验证
5. 任一层成功 → 结果注入主流程；失败 → 下一层
6. 全部失败 → 安全层输出错误结论报告（缺失资源 + 已尝试路径 + 停止原因 + 用户建议 + 部分成果）
7. 记录到 missing_skills.md（skill 演化需求库）+ 探索成功模式存入 pattern 库

### 5.7 三道安全停止线

- τ 探索预算耗尽（>30%）→ 停止
- 置信度 < 0.5 → 停止
- 破坏性风险（git push --force/删文件/生产部署）→ 立即停止，不探索

### 5.8 预判 + 后台预探索流程

1. 编排层规划阶段预判可能缺失的 skill
2. 提前启动 subAgent 后台预探索（与主流程并行）
3. 主流程到缺失节点时：探索成功→注入结果（零等待）；探索失败→直接进安全层（不重复探索）

### 5.9 任务归档流程

1. 编排层固化文件路径到 task_skill.md
2. mkdir history/YYYY-MM/ → mv task_skill.md 到该目录
3. 更新月度任务索引（含固化文档路径）
4. 探索成功模式存 pattern 库；缺失记 missing_skills.md

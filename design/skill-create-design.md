# Skill 创建设计原则

当前编排系统以 `orchestrator` 为统一入口。新增或修改主 Skill、原子 Skill 时，必须遵守本设计原则，并兼容 `Fast Path`、`Durable Path`、DAG、状态恢复、分级校验和任务归档机制。

## 一、总体原则

1. 所有用户意图优先匹配主 Skill，不得直接匹配或执行业务原子 Skill。
2. 主 Skill 负责完整领域目标的拆解、原子 Skill 编排、执行顺序、结果汇总和失败决策。
3. 原子 Skill 只承担单一、可验证的最小职责。
4. 所有依赖、路由、确认、状态、错误和完成标准必须可声明、可校验、可追踪。
5. 不确定风险、兼容性或副作用时，按更高风险处理，不得通过隐式约定继续执行。

## 二、主 Skill 与原子 Skill 边界

### 2.1 主 Skill

主 Skill 必须说明：

- 解决的完整领域问题；
- 适用场景和不适用场景；
- 任务拆解方式；
- 原子 Skill 的选择和编排方式；
- 执行顺序、失败处理和完成标准；
- 需要用户确认的节点和不可逆操作。

主 Skill 应负责领域级决策，不得把多个互不相关的职责强行合并，也不得通过隐式步骤绕过已声明的依赖关系。

### 2.2 原子 Skill

原子 Skill 必须满足：

- 单一职责；
- 可独立描述执行边界；
- 可独立判断成功或失败；
- 在所属主 Skill 中具有稳定的复用价值；
- 需要独立重试、状态跟踪或错误定位时才拆分。

以下情况不应拆分为原子 Skill：

- 仅包含一条没有独立校验价值的简单操作；
- 只是主 Skill 的提示语或临时推理步骤；
- 仅为增加 Skill 数量而人为拆分；
- 无法独立定义完成条件。

### 2.3 边界判定

| 判定问题 | 归类 |
| --- | --- |
| 是否负责完整领域目标 | 主 Skill |
| 是否只完成一个可验证动作 | 原子 Skill |
| 是否需要选择和调度其他步骤 | 主 Skill |
| 是否需要独立重试或失败定位 | 可拆分为原子 Skill |
| 是否只能依赖一个所属主 Skill | 原子 Skill |
| 是否无法独立定义完成条件 | 不应拆分 |

## 三、依赖关系与 DAG

1. 主 Skill 负责声明和维护其原子 Skill 的编排依赖。
2. 依赖关系只表示 `orchestrator` 的调度先后，不表示原子 Skill 在内部直接调用另一个原子 Skill。
3. 原子 Skill 不得隐式调用未声明的节点；需要组合多个原子步骤时，必须由主 Skill 编排。
4. 依赖图必须是有向无环图（DAG）。
5. 创建或修改 Skill 时，必须执行：
   - 依赖存在性检查；
   - 所属关系检查；
   - 循环依赖检查；
   - 稳定拓扑排序；
   - 无依赖节点和可并行层识别。
6. 禁止缺失依赖、循环依赖、孤立原子 Skill 和跨主 Skill 越权依赖。
7. 可并行层只表示依赖关系允许并行，不代表必须并行执行。并行前还必须确认不存在文件冲突、共享资源冲突、外部写入冲突和顺序依赖。
8. 默认采用 `serial_by_default`，只有明确满足安全条件时才允许并行。

## 四、Fast Path 与 Durable Path

### 4.1 Fast Path

只有同时满足以下条件，才允许使用 Fast Path：

- 单一主 Skill；
- 无多阶段依赖或复杂 DAG；
- 低风险；
- 无需用户确认；
- 不需要暂停、恢复或跨会话执行；
- 不涉及不可逆外部副作用；
- 不需要完整任务持久化和归档。

### 4.2 Durable Path

任一条件成立，必须进入 Durable Path：

- 涉及多个主 Skill、原子 Skill 依赖或多阶段 DAG；
- 需要用户确认；
- 涉及写入、删除、覆盖、部署、迁移、权限、凭证、Git 写操作或外部系统写入；
- 需要重试、暂停、恢复、断点续作或跨会话执行；
- 存在低置信度、匹配歧义或需求不完整；
- 需要完整执行日志、状态记录或归档。

### 4.3 路由升级

Fast Path 只能单向升级为 Durable Path：

```text
Fast Path → Durable Path
```

升级时必须保留已确定的意图、依赖关系、当前阶段、节点状态、校验结果和失败原因。升级后不得重复执行已确认成功且无副作用的节点；可能产生副作用的节点必须先核验实际结果。

## 五、确认机制与不可逆操作

以下操作必须在实际副作用发生前取得用户确认：

- 删除文件、目录或 Skill；
- 覆盖用户已有内容；
- 修改注册表、全局配置、hooks、权限或命令入口；
- 修改版本文件或发布归档；
- Git `commit`、`merge`、`rebase`、`tag`、`push`；
- 生产部署；
- 数据迁移或批量修改；
- 外部系统写入；
- 无法可靠回滚的操作。

确认信息至少说明：

- 将执行的动作；
- 影响范围和目标对象；
- 是否可回滚；
- 取消后的状态；
- 可能产生的副作用。

确认规则：

1. 用户未确认时，只能停留在规划、检查或预览阶段。
2. 不得通过自动重试、降级路径或自主探索绕过确认。
3. 执行计划发生实质变化时，必须重新确认。
4. 风险不明确、无法证明回滚条件或前置校验失败时，必须停止。
5. 确认中断、权限不足或外部结果不确定时，不得继续后续副作用步骤。

## 六、状态机、失败处理与恢复

Skill 或任务节点至少支持以下状态：

```text
待执行 → 执行中 → 已完成
              ├→ 失败
              ├→ 暂停
              └→ 待恢复
```

状态含义：

- `待执行`：依赖已满足但尚未开始；
- `执行中`：节点已开始，不能被重复启动；
- `已完成`：完成标准和必要校验均已通过；
- `失败`：无法达到完成标准，已记录失败分类和影响；
- `暂停`：等待用户确认、外部资源或人工处理；
- `待恢复`：任务可以继续，但必须先核验已有结果和副作用。

状态迁移约束：

1. 不允许从 `失败` 直接标记为 `已完成`。
2. 重试前必须记录上一次失败原因和影响。
3. 已完成节点不可无条件重复执行。
4. 恢复时优先读取持久化状态，不得覆盖历史结果和错误记录。
5. 多个活动任务同时存在时，不得自动覆盖、合并或忽略。
6. 每次状态迁移必须记录迁移原因和发生阶段。

恢复策略：

- 无副作用节点可基于状态直接恢复或重试；
- 可能有副作用的节点，恢复前必须验证实际结果；
- 无法判断是否已产生副作用时，必须暂停并请求人工确认；
- 依赖节点失败时，所有后续依赖节点保持阻塞；
- 只能从最近一个可验证状态继续，不得跳过未完成的前置依赖。

## 七、错误分类与标准处理

| 错误类别 | 示例 | 默认处理 |
| --- | --- | --- |
| `validation_error` | 需求不完整、前置条件不满足 | 停止并请求补充 |
| `routing_error` | 无匹配、匹配冲突、职责边界不清 | 请求选择或进入 Durable Path |
| `dependency_error` | 依赖缺失、循环依赖、跨域依赖 | 执行前阻断 |
| `execution_error` | Skill 执行失败、工具失败 | 按策略重试或失败 |
| `permission_error` | 无权限、用户未确认 | 暂停，不得绕过 |
| `side_effect_error` | 写入、删除、部署结果不确定 | 进入恢复核验 |
| `timeout_error` | 超时、预算耗尽 | 暂停或失败 |
| `consistency_error` | 注册表、路径、版本不一致 | 阻断执行或发布 |
| `concurrency_error` | 重复执行、锁冲突、活动任务冲突 | 保留原任务并返回冲突 |
| `compatibility_error` | Skill 版本或任务格式不兼容 | 迁移、暂停或阻断 |

每次失败、暂停、升级或部分完成时，必须说明：

- 当前状态；
- 错误分类；
- 发生阶段；
- 受影响节点；
- 是否已产生副作用；
- 是否允许重试；
- 是否需要用户确认；
- 下一步动作。

禁止只返回“执行失败”“处理异常”“请稍后重试”等无上下文结论。

## 八、可校验的完成标准

主 Skill 和原子 Skill 都必须提供可执行的验收条件。完成标准必须：

- 使用可观察结果描述；
- 可以由人工或自动检查；
- 明确通过、失败或部分完成；
- 对文件操作可检查文件存在、内容变化或结构正确；
- 对分析操作可检查报告是否覆盖声明维度；
- 对修改操作可检查变更范围和验证结果；
- 对流程操作可检查所有必需节点是否完成；
- 不使用“基本完成”“处理妥当”“符合预期”等模糊描述。

建议每个 Skill 至少明确：

```markdown
- 必须完成的节点：
- 必须通过的检查：
- 允许的部分完成条件：
- 失败判定：
- 需要人工确认的情况：
```

整体结果限定为：

- `passed`：所有必需标准通过；
- `partial`：部分标准通过，剩余项已明确；
- `failed`：关键标准未通过；
- `blocked`：因依赖、权限或确认无法继续。

## 九、可观测性

执行过程至少记录：

- 选中的主 Skill 和选择理由；
- 执行路径：`Fast` 或 `Durable`；
- 路由升级原因；
- 依赖检查结果和 DAG 执行层级；
- 每个节点的开始、结束、状态和重试次数；
- 关键校验结果；
- 错误分类和影响范围；
- 用户确认、暂停、恢复和人工介入记录；
- 最终状态和未完成项。

可观测性分为执行控制事件和面向用户的执行摘要两层。事件顺序必须能够还原执行过程，失败事件不得覆盖成功事件，恢复操作必须关联原任务。禁止记录 token、密码、凭证等敏感信息。Fast Path 可使用轻量记录，但升级后必须补齐 Durable Path 所需记录。

## 十、注册表一致性

新增、删除、重命名、合并或拆分 Skill 时，必须同步检查：

- 主 Skill 是否存在于主 Skill 注册表；
- 原子 Skill 是否存在于原子 Skill 注册表；
- 主/原子归属与实际目录是否一致；
- 注册路径是否指向真实存在的 Skill 文件；
- 注册状态是否与实际可执行状态一致；
- 依赖节点是否均已注册；
- 已删除或合并的 Skill 是否仍被引用；
- 相关 slash command 或入口配置是否仍然有效；
- 注册表统计和索引信息是否准确。

注册一致性检查清单：

```markdown
- [ ] Skill 名称、目录和注册名一致
- [ ] 主/原子归属一致
- [ ] 注册路径真实存在
- [ ] 依赖节点均已注册
- [ ] 不存在循环或孤立原子 Skill
- [ ] 已删除 Skill 不再被引用
- [ ] 相关命令入口有效
- [ ] 注册表统计和索引信息未失真
```

新增主 Skill 不要求必须创建原子 Skill；只有实际声明原子 Skill 时，才同步维护原子 Skill 注册信息。

## 十一、版本兼容与迁移

1. Skill 文档版本、执行规则版本和项目发布版本分别管理，不得混为一谈。
2. 仅补充说明且不改变既有行为，属于兼容变更。
3. 改变职责边界、依赖关系、节点名称、状态含义、完成标准、安全边界或副作用行为，属于不兼容变更。
4. 不兼容变更必须提供迁移说明，并重新执行依赖、注册和完成标准校验。
5. 旧任务不得被新版本静默覆盖。
6. 恢复旧任务时，能兼容读取则继续；不能兼容读取则暂停并说明原因；不得强行映射新旧状态并丢失信息。
7. 普通文案修订不应自动修改项目发布版本；项目版本、CHANGELOG 和发布归档必须按项目工作流处理。

## 十二、并发与幂等

1. 同一个任务只能有一个有效执行者。
2. 同一原子 Skill 在同一任务中不得被重复启动。
3. 并行执行前必须确认不存在文件写入冲突、共享资源冲突、外部系统重复写入风险和顺序依赖。
4. 对外部副作用操作，必须使用任务、节点或等效标识避免重复提交。
5. 重试前必须判断上一次执行是否已经成功产生副作用。
6. 并发冲突时保留原任务状态，不覆盖、不合并、不静默丢弃。
7. 多个活动任务需要由用户或编排层明确选择。
8. 幂等失败和锁冲突必须按标准错误分类处理，不得当作普通成功或普通重试处理。

## 十三、Skill 变更影响分析

修改 Skill 前，必须分析：

- 主 Skill 职责是否变化；
- 原子 Skill 是否新增、删除、重命名或迁移；
- DAG 是否变化；
- 是否影响 Fast / Durable Path 路由；
- 是否引入新的确认点或不可逆操作；
- 状态机、错误分类或恢复策略是否变化；
- 注册表、slash command 或入口配置是否需要同步；
- 旧任务和旧版本是否仍可恢复；
- 是否影响其他 Skill 的匹配关键词或职责边界；
- 是否影响并发、幂等或归档行为。

影响级别：

- `low`：仅澄清文档，不改变行为；
- `medium`：新增节点、校验或路由条件；
- `high`：改变职责边界、依赖、状态、外部副作用或兼容性。

处理要求：

- `low`：可直接进行文档修改；
- `medium`：必须同步更新流程、检查清单和兼容说明；
- `high`：先输出影响范围、迁移方案和待确认事项，再执行实际变更。

## 十四、创建与变更检查清单

```markdown
- [ ] 已明确主 Skill 或原子 Skill 的职责边界
- [ ] 已检查依赖存在性、归属和循环依赖
- [ ] 已确认执行路径和可能的 Durable 升级条件
- [ ] 已识别不可逆操作和用户确认节点
- [ ] 已定义状态迁移、失败处理和恢复策略
- [ ] 已定义可校验的完成标准
- [ ] 已定义错误分类和失败后的下一步
- [ ] 已补充必要的可观测性记录
- [ ] 已完成注册表和入口配置一致性检查
- [ ] 已评估版本兼容和旧任务迁移影响
- [ ] 已检查并发、重复执行和幂等风险
- [ ] 已完成变更影响分析
```

## 十五、严令禁止

1. 禁止绕过主 Skill，直接由用户意图触发业务原子 Skill。
2. 禁止业务原子 Skill 跨主 Skill 调用。
3. 禁止一个原子 Skill 归属多个主 Skill。
4. 禁止出现无所属的原子 Skill。
5. 禁止原子 Skill 内部隐式调用其他原子 Skill；组合必须由主 Skill 编排。
6. 禁止使用未声明、缺失、循环或跨域依赖。
7. 禁止在未确认情况下执行不可逆操作。
8. 禁止将失败节点直接标记为成功。
9. 禁止覆盖已有活动任务、错误记录或历史结果。
10. 禁止注册重复、孤立或路径失效的 Skill。
11. 禁止使用不可校验的完成标准。
12. 禁止在版本不兼容时静默恢复旧任务。
13. 禁止使用无结构化自由文本传递关键参数。
14. 禁止使用“其他”“视情况”“后续处理”等模糊表述替代明确规则。

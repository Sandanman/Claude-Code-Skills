Skills架构设计规范（按模块顺序整理）

1、整体设计

（1）总则
整体通过编排skill（小模型）执行任务，规划可控工作流（大模型或者更合适的模型进行处理），高质量完成整个任务（任务边界限定）。

- 编排skill：全局编排器-只编排主skills，需要执行多个skill时，对skill选择、调度编排、输出全局报告。决定做什么、用谁做、按什么顺序做、预算多少。
- 主skill：领域编排器-只编排自己的原子skill，主要做什么？选择原子skill、按照依赖关系决定原子skill的执行顺序（串行、并行）、整合业务结果。决定这件事怎么做才专业。
- 原子skill：主skill可拆分成的最小功能的实现单元，可分步骤串行执行、分模块并行执行。具体的操作实施。

准则依据：提升质量、缩短时耗、减少Token
- 更准确的理解意图
- 更准确的选择路径
- 更准确的验证结果
- 更准确的积累经验

（2）工作流
（2.1）用户输入任务
（2.2）分析用户意图（意图建模？？？），拆分任务类型
- 单一任务
- 流程任务（可并行任务）

（2.3）依据skill注册表对任务进行skill匹配
- skill注册模式 - 现有模式
- skill探索模式 - 自主探索（优先本地）skill，更好的利用网络所有的skill
- skill补充模式 - 对于缺失的skill进行记录和后续完成

- 单一任务：直接匹配主skill
- 复杂任务：通过编排skill生成工作流（对并行子任务/subAgent/原子skill，进行信息收拢；对串行流程，上一节点的输出作为下一个节点的输入，将数据流贯穿整个协作链）

（2.4）补充：针对系统已注册skill是否满足工作流？
- 现有skill完全满足整个工作流
- 缺失部分节点的skill，但是可以自主探索执行该节点任务，或可以通过暂时留缺保证工作流顺利执行完毕后再提示用户补充留缺或者补充该缺失的skill
- 完全不满足时，自主探索技能，规划工作流。（需要严格遵守的规范）
- 并行任务：原子skill、拆分子任务、subAgent 使用哪个？规则？
- 编排skill结合任务，预判缺失的技能，通过subAgent或者其他提前搜索功能或其他方式，减少工作流中过的等待时间
- 自主升级？？？

（3）完整工作流

（3.1）总体入口流程
1. 用户输入 → 编排 skill 接管
2. 意图识别 + 复杂度评分（complexity_score）
3. 路径分流：
   - complexity < 4 → 路径 A（委托主 skill）
   - complexity ≥ 4 → 路径 B（编排层统一编排）

（3.2）路径 A：简单任务执行流程
1. 编排层从 skills_register.md 匹配单个主 skill
2. 无匹配 → 记 missing_skills.md + 自主兜底；多匹配 → 用户选择
3. 委托主 skill 全权处理（编排层不读 SKILL.md、不参与执行）
4. 主 skill 读自己 SKILL.md 的第 4 章"简单任务执行流程"
5. 主 skill 三动作自跑：
   - 选：按第 2 章选择规则确定原子 skill 子集
   - 编：按第 3 章 DAG 构建执行顺序（并行层用 subagent，串行贯穿数据流）
   - 执行+汇总：逐层执行原子 skill → 套第 5 章模板汇总业务结果
6. 主 skill 返回业务结果 → 编排层输出给用户
7. task_skill.md 用简化版（主 skill 级状态）

（3.3）路径 B：复杂任务执行流程
1. 编排层从 skills_register.md 匹配多个主 skill 组合
2. 读取各主 skill 的 SKILL.md 声明（第 1-3 章：原子skill池/选择规则/DAG）
3. 按选择规则确定原子 skill 子集
4. 合并为全局 DAG（跨主skill边界优化并行层）
5. 全局 τ/Token/Duration 预算分配与监控
6. 统一执行原子 skill（Task Folding 折叠、Pattern Mining 复用、Skill Stacking 共享上下文）
7. 执行完毕 → 委托各主 skill 读第 5 章模板汇总各自业务结果
8. 编排层输出：全局三指标报告 + 各主 skill 业务汇总
9. task_skill.md 用完整版（原子 skill 级状态）+ 归档到 history/YYYY-MM/

（3.4）简单→复杂动态升级流程
1. 主 skill 执行中发现复杂度上升（需求模糊/依赖其他领域）
2. 触发升级判定：complexity_re-estimate ≥ 4
3. 上报编排层 → 接管 → 切换为路径 B（合并 DAG + 统一执行）

（3.5）SKILL.md 双模式读取流程
- 路径 A：主 skill 读第 2+3+4+5 章（自跑全链路）
- 路径 B：编排层读第 1+2+3 章（代选+合并DAG+统一执行），执行后委托主 skill 读第 5 章（汇总）

（3.6）Skill 缺失三层探索流程
1. 检测到缺失（简单任务原子skill缺失 / 复杂任务主skill缺失）
2. 第一层·本地扫描：搜 .claude/skills/ 相近 skill + 可组合替代 + pattern 库复用
3. 第二层·subAgent 近场探索：启动 general-purpose subAgent 用基础工具自主实现
4. 第三层·远场探索：WebSearch 搜方案 + subAgent 自主实现 + 验证
5. 任一层成功 → 结果注入主流程；失败 → 下一层
6. 全部失败 → 安全层输出错误结论报告（缺失资源 + 已尝试路径 + 停止原因 + 用户建议 + 部分成果）
7. 记录到 missing_skills.md（skill 演化需求库）+ 探索成功模式存入 pattern 库

（3.7）三道安全停止线
- τ 探索预算耗尽（>30%）→ 停止
- 置信度 < 0.5 → 停止
- 破坏性风险（git push --force/删文件/生产部署）→ 立即停止，不探索

（3.8）预判 + 后台预探索流程
1. 编排层规划阶段预判可能缺失的 skill
2. 提前启动 subAgent 后台预探索（与主流程并行）
3. 主流程到缺失节点时：探索成功→注入结果（零等待）；探索失败→直接进安全层（不重复探索）

（3.9）任务归档流程
1. 编排层固化文件路径到 task_skill.md
2. mkdir history/YYYY-MM/ → mv task_skill.md 到该目录
3. 更新月度任务索引（含固化文档路径）
4. 探索成功模式存 pattern 库；缺失记 missing_skills.md

5、Skill缺失的智驾雷达式自主探索

（1）核心原则
当 skill 缺失时，编排 skill 依照智驾雷达系统的逻辑自主探索实现，如果实在没有办法完成，则输出错误信息结论给用户。
缺失不等于失败，先探索，实在不行才报错。这与 design.md 的"自主探索模式"和"skill 补充模式"完全对齐。

（2）智驾雷达类比：四层处理模型
- 感知层（雷达扫描）→ 缺失检测 + 资源扫描：识别缺失的 skill 功能，扫描本地/网络可用资源
- 决策层（路径规划）→ 替代方案探索：规划替代路径（组合现有 skill / subAgent 自主实现）
- 执行层（自主行驶）→ 自主尝试执行：用替代方案尝试完成任务
- 安全层（紧急制动）→ 错误结论输出：实在无法完成 → 输出明确错误信息给用户

核心理念：雷达系统的目标不是"遇到障碍就停车"，而是"尽可能绕过障碍到达目的地，只有无路可走才停车"。

（3）三层探索逻辑（由近及远）

（3.1）第一层：本地雷达扫描（感知替代资源）
[缺失检测] 需要原子skill X，但池中没有
    ↓
[本地扫描]
   ├─ 在 .claude/skills/ 全目录搜索功能相近的 skill（可能未注册但存在）
   ├─ 检查是否有可组合的现有原子 skill 能替代 X 的功能
   └─ 检查 pattern 库是否有历史相似任务的执行模式可复用
    ↓
找到替代 → 用替代方案执行
未找到  → 进入第二层

（3.2）第二层：subAgent 近场探索（自主绕行）
[启动 general-purpose subAgent]
   ├─ 传入：任务上下文 + 缺失skill的功能描述
   ├─ subAgent 自主分析：能否用基础工具（Read/Write/Bash/Grep等）完成该步骤
   ├─ subAgent 自主尝试实现缺失功能
   └─ 返回：成功结果 OR 探索失败报告
    ↓
成功 → 继续后续流程
失败 → 进入第三层

关键：subAgent 在独立上下文探索，不污染主流程的 τ 预算，失败也不影响主流程的状态。

（3.3）第三层：远场探索（网络 + 自主实现）
[网络探索 + 自主实现]
   ├─ WebSearch 搜索相关方案/代码/文档
   ├─ 基于搜索结果，subAgent 自主实现缺失功能
   ├─ 验证实现质量（如能验证）
   └─ 返回：成功 OR 最终失败
    ↓
成功 → 执行 + 记录到 missing_skills.md（后续补充正式 skill）
失败 → 进入安全层

（4）三道安全停止线
智驾系统有"安全边界"，skill 系统同样需要三道停止线，避免无限探索耗尽资源：
- 停止线1·τ 探索预算耗尽：探索消耗 τ 超过总预算 30% → 停止探索，进入安全层
- 停止线2·置信度阈值：自主探索成功概率评估 < 0.5 → 停止探索，进入安全层
- 停止线3·破坏性风险：涉及生产环境/不可逆操作/安全敏感 → 立即停止，进入安全层（不探索）

第三道线最重要：涉及 git push --force、删除文件、生产部署等不可逆操作时，不允许自主探索，必须直接报错让用户决策。这是智驾系统的"绝对安全原则"。

（5）简单任务 vs 复杂任务的缺失处理差异

（5.1）简单任务（原子 skill 缺失）
[主 skill 执行中] 发现原子skill X 缺失
    ↓
主 skill 自己尝试第一层（本地扫描，在自己的领域内）
    ↓ 找不到
上报编排层
    ↓
编排层启动第二层（subAgent 探索）
    ↓ 失败
编排层启动第三层（网络探索）
    ↓ 失败
→ 安全层：输出错误结论

（5.2）复杂任务（主 skill 缺失）
[编排层规划阶段] 发现需要主 skill Y，但未注册
    ↓
编排层直接启动三层探索（跳过主skill自探索，因为主skill本身缺失）
   ├─ 第一层：本地扫描是否有未注册的 skill 可用
   ├─ 第二层：subAgent 尝试用现有主 skill 组合替代
   └─ 第三层：subAgent 自主实现该领域逻辑
    ↓ 全部失败
→ 安全层：输出错误结论

（6）错误信息输出规范（安全层）
错误信息不应该是简单的"任务失败"，而应该是雷达系统的"事故报告"，让用户清楚知道发生了什么、可以怎么做：

【⚠️ 任务无法完成 — 探索报告】

缺失资源：
- 缺失 skill：{skill名称}（{主skill/原子skill}）
- 功能描述：{该skill应承担的功能}
- 缺失位置：{在DAG中的位置/在执行流程的哪一步}

已尝试的探索路径：
1. ✗ 本地扫描：未找到功能相近的替代 skill
2. ✗ subAgent 自主探索：{探索结果摘要}，置信度 0.3
3. ✗ 网络探索：{搜索结果摘要}，无可用方案

停止原因：
- 触发停止线：{τ预算耗尽 / 置信度不足 / 破坏性风险}

给用户的建议：
- 选项1：补充缺失的 skill（参考 missing_skills.md 的记录）
- 选项2：手动完成该步骤后重新发起任务
- 选项3：调整任务描述，规避该功能需求
- 选项4：如确需该能力，可创建 skill 后重试

部分成果（如有）：
- 已完成的步骤：{列出已完成的部分}
- 可复用的中间产物：{文件/上下文}

关键：错误输出是结论性的、可行动的，不是模糊的"失败了"。

（7）预判能力（雷达的前瞻扫描）
智驾雷达的精髓是提前感知，不是"撞上去了再绕"。映射到 skill 系统：编排阶段就预判缺失。

[编排层规划阶段]
   ├─ 意图识别后，预判任务可能需要的 skill 集合
   ├─ 对比 skills_register.md，识别可能缺失的 skill
   ├─ 提前启动 subAgent 预探索（后台并行）   ← 关键
   └─ 规划工作流时，为可能缺失的节点预留"探索窗口"

收益：执行到缺失节点时，探索可能已完成，零等待。这正是 design.md 说的"减少工作流中的等待时间"。

预探索的 subAgent 后台运行：
编排层规划任务
    ↓
    ├─ 主流程：开始执行已确定的 skill
    └─ 后台 subAgent：并行预探索可能缺失的 skill  ← 同时进行
            ↓ 探索成功
        结果注入主流程的缺失节点
            ↓ 探索失败
        主流程到该节点时直接进入安全层（不重复探索）

（8）与现有机制的整合

（8.1）missing_skills.md 的角色升级
从"缺失清单"升级为"skill 演化的需求库" — 每次探索失败都是一次需求收集，积累到一定程度可批量补充 skill。

记录格式：
- 缺失类型：主skill / 原子skill
- 功能描述：{应承担的功能}
- 触发场景：{什么任务需要它}
- 已探索路径：{三层探索的记录}
- 探索失败原因：{为什么没成功}
- 建议补充方式：{基于探索经验给出的补充建议}
- 临时替代方案：{如果有 subAgent 自主实现的临时逻辑，记录下来}

（8.2）pattern 库的复用
探索成功后，把"自主探索的执行模式"存入 pattern 库。下次相似任务可直接复用探索结果，不用重新探索。这是 K4 Pattern Mining 在探索场景的应用。

（9）设计要点

（9.1）探索预算独立分配：探索消耗的 τ 从"探索专用预算"扣除，不吃主流程执行预算。
任务总 τ 预算
  ├─ 主流程执行：70%
  └─ 探索储备：30%（仅在缺失时启用，不用则归还）

（9.2）探索的幂等性：同一缺失节点的探索结果可缓存，不重复探索。探索失败也缓存"失败结论"，避免重试浪费。

（9.3）用户可见性：探索过程对用户透明可见（流式输出），让用户知道"系统在努力找替代方案"，而不是"卡住了"。

（9.4）探索成功后的 skill 沉淀：如果 subAgent 自主实现的逻辑被多次（如 ≥3 次）探索复用，应升级为正式的原子 skill，写入 .claude/skills/。这是系统的"自主进化"能力。

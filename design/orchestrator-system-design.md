# Orchestrator 系统设计

> 本文整合 `design/about.md`、`design/design-spec.md`、`design/design.md`、`design/skill-design.md`、`design/talk.md` 和 `design/skill-create-design.md`。
>
> 本文以当前 `.claude/skills` 下的实际文件、注册表、任务模板和 `.claude/settings.json` 为事实依据。文中明确区分“当前协议/目录能力”和“历史设计或待确认方案”。Skill 当前主要由 Markdown 指令驱动，不应将文档中规定的流程误解为已经存在独立的运行时调度器。

## 1. 文档范围与证据等级

### 1.1 文档目标

本文定义 Claude Code Skills 项目的统一 Orchestrator 体系，包括：

- Orchestrator、主 Skill 和原子 Skill 的职责边界；
- 用户请求从识别、匹配、路由到执行、校验和归档的流程；
- Fast Path 与 Durable Path 的适用条件；
- DAG、任务状态、共享上下文、恢复和错误处理规则；
- Skill 的创建、修改、注册和兼容迁移规则；
- 当前能力限制、历史方案和需要进一步确认的设计项。

### 1.2 证据等级

| 等级 | 含义 | 本文写法 |
| --- | --- | --- |
| 当前规范 | 当前 `SKILL.md`、注册表、模板或配置明确规定 | 使用“必须”“当前支持”“当前规则” |
| 当前目录能力 | 文件、目录或历史任务确实存在，但没有独立运行时保证 | 使用“存在”“可由 Claude 按协议执行” |
| 历史设计 | 来源文档提出过，但当前实现无法确认 | 标注“历史方案”“设计目标” |
| 待确认 | 需要产品或架构决策，不能由当前文件推断 | 单独列入待确认项 |

### 1.3 当前实现边界

当前项目不是传统意义上的编排服务或任务调度引擎：

- Skill 的主体是 `SKILL.md` Markdown 指令和相关注册表；
- 没有独立的意图识别程序、Skill 匹配器、DAG 执行器、并行调度器或状态数据库；
- 任务状态、日志、共享上下文和归档以 Markdown 文件协议表示；
- Claude 根据 Skill 规范调用 `Read`、`Write`、`Edit`、`Bash`、`Agent` 等工具完成实际动作；
- `impl_status: action_based` 表示 Skill 依赖工具动作执行，不等价于已有独立运行时；
- hooks 主要提供提示、权限和会话管理，不会自动识别意图、生成 DAG 或执行 Skill。

因此，本文中的“执行”“自动”“校验”和“归档”，在当前阶段应理解为“编排协议要求 Claude 执行”，除非另有代码或配置证据。

## 2. 系统分层

```text
用户请求
    ↓
Orchestrator（统一入口，编排主 Skill）
    ↓
主 Skill（领域级处理，编排所属原子 Skill）
    ↓
原子 Skill（单一、可验证动作）
    ↓
工具调用与项目文件
```

### 2.1 Orchestrator

Orchestrator 是统一任务入口，负责：

- 检查自身安装和入口配置；
- 分析请求意图和任务风险；
- 从主 Skill 注册表匹配一个或多个主 Skill；
- 选择 Fast Path 或 Durable Path；
- 检查依赖并规划 DAG；
- 控制任务状态、执行顺序、共享上下文和恢复；
- 进行结果校验并输出执行摘要；
- 对 Durable Path 任务进行归档。

Orchestrator 只编排主 Skill，不应绕过主 Skill 直接以用户意图触发业务原子 Skill。

### 2.2 主 Skill

主 Skill 负责一个完整业务领域的专业处理，包括：

- 领域目标、适用范围和不适用范围；
- 所属原子 Skill 的选择；
- 原子 Skill 的依赖和执行顺序；
- 领域级失败处理和结果汇总；
- 领域完成标准和用户确认节点。

主 Skill 不应把互不相关的职责强行合并，也不得通过隐式步骤绕过已声明依赖。

### 2.3 原子 Skill

原子 Skill 是主 Skill 可拆分出的最小功能单元，必须：

- 具有单一职责；
- 能够独立描述执行边界；
- 能够独立判断成功或失败；
- 在所属主 Skill 中具有稳定复用价值；
- 在需要独立重试、状态跟踪或错误定位时再进行拆分。

不应将只有一条简单操作、临时推理步骤或无法独立定义完成条件的内容拆为原子 Skill。当前项目正式使用的术语是 `atomic skill` / `atomic-skills`，`subskill` 不是已确认的独立运行时概念。

## 3. 注册表与启动检查

### 3.1 注册表

当前注册关系为：

- 主 Skill 注册表：`.claude/skills/orchestrator/skills_register.md`；
- 原子 Skill 注册表：`.claude/skills/orchestrator/atomic_skills_register.md`；
- 主 Skill 实体：`.claude/skills/<skill-name>/SKILL.md`；
- 原子 Skill 通常位于所属主 Skill 的 `atomic-skills/` 目录中；
- Slash command 入口配置位于 `.claude/settings.local.json` 的 `commands`（个人本地配置）。

未注册的主 Skill 不允许被 Orchestrator 选择和执行。新增、删除、重命名、合并或拆分 Skill 时，必须同步检查注册表、实际路径、依赖和 command 入口。

### 3.2 Orchestrator 启动前检查

每次任务只做轻量判断：`orchestrator` 能被调起（在可用 Skill 列表中或 `.claude/skills/orchestrator/SKILL.md` 存在）即直接编排；不存在时不使用编排系统，按实际可用 Skill 执行。

完整安装检查不属于每次任务，仅在安装或同步后（`cheers`）或用户明确要求时执行，三项须同时满足：

1. `.claude/skills/orchestrator/SKILL.md` 存在，且 frontmatter 的 `name` 为 `orchestrator`；
2. 主 Skill 注册表中存在路径正确且 `status: 启用` 的 `orchestrator` 条目；
3. `.claude/settings.local.json` 的 `commands` 中存在 `orchestrator`（兼容检查 `.claude/settings.json`）。

缺失时输出缺失项和安装地址，不自动修复。

## 4. 统一编排流程

当前规范链路如下：

```text
用户请求
  → 启动前检查
  → 意图识别与路由判断
  → 主 Skill 匹配与读取
  → Fast Path 或 Durable Path
  → 任务规划与依赖检查
  → 原子 Skill 执行
  → 分级结果校验
  → 输出执行摘要和业务结果
  → Durable Path 按需归档
```

确定主 Skill 后，执行摘要必须提供可观测信息：

- `main_skill`；
- 匹配关键词；
- 匹配分数，无法可靠计算时为 `unknown`；
- 选择理由；
- 声明依赖；
- 执行路径；
- 任务 ID、状态和校验级别。

### 4.1 意图建模

当前意图结构至少包含：

- `domain`：业务领域；
- `action`：用户动作；
- `target`：目标对象；
- `constraints`：约束条件；
- `keywords`：触发关键词；
- `success_criteria`：用户成功标准；
- `complexity_assessment`：复杂度判断；
- `confidence`：识别置信度；
- `risk_level`：风险级别；
- `statefulness`：是否需要持续状态；
- `ambiguity`：歧义；
- `requires_confirmation`：是否需要用户确认。

这些字段目前属于协议层结构，由 Claude 依据请求和项目上下文生成，不是独立分类器的输出。

### 4.2 主 Skill 匹配

匹配应综合比较：

- 领域和动作；
- 目标类型；
- 触发关键词；
- Skill 能力描述；
- 声明依赖和适用范围。

处理规则：

- 唯一且置信度足够的匹配：直接选择，不重复澄清；
- 多个候选或分数接近：展示必要候选并请求用户选择；
- 无匹配：记录缺失能力，判断是否可以安全地使用已有能力完成；
- 未注册主 Skill：不得直接执行其目录内容。

当前注册表存在匹配关键词和能力描述，但没有独立、可复现的评分程序。历史文档中的固定权重和复杂度阈值不能当作运行时客观计算结果。

## 5. Fast Path 与 Durable Path

### 5.1 Fast Path

只有同时满足以下条件时才使用 Fast Path：

- 单一主 Skill；
- 任务明确、低风险、高置信度；
- 无多阶段依赖或复杂 DAG；
- 不需要用户确认；
- 不涉及不可逆外部副作用；
- 不需要暂停、恢复、跨会话执行或完整归档。

流程：

```text
意图识别 → 主 Skill 匹配 → 读取 Skill → 执行 → L0 校验 → 输出
```

Fast Path 默认跳过历史检索、完整 DAG、完整任务模板、反思循环和月度归档，不创建完整任务文件。但仍必须执行主 Skill 的最低完成标准和安全检查。

### 5.2 Durable Path

任一条件成立时必须使用 Durable Path：

- 多个主 Skill、多个阶段或原子 Skill 依赖；
- 低置信度、匹配歧义或需求不完整；
- 需要用户确认；
- 涉及写入、删除、覆盖、部署、迁移、权限、凭证、Git 写操作或外部系统写入；
- 需要重试、暂停、恢复、断点续作或跨会话执行；
- 需要跨步骤共享上下文、完整执行日志或归档。

流程包括历史按需检索、依赖和 DAG 检查、任务状态、执行日志、共享上下文、L1/L2 校验和归档。

### 5.3 路由规则与动态升级

复杂度只是路由输入，不能单独决定安全级别。应综合 `confidence`、`risk_level`、`statefulness`、`ambiguity` 和 `requires_confirmation`。

以下操作即使步骤少，也不能仅因复杂度低而使用 Fast Path：删除、覆盖、部署、权限或凭证操作、Git 写操作、数据迁移和外部系统写入。

路由只能单向升级：

```text
Fast Path → Durable Path
```

升级时保留已有意图、匹配结果、依赖、当前阶段、节点状态、校验结果和失败原因。已确认成功且无副作用的节点不重复执行；可能产生副作用的节点必须先核验实际结果。

## 6. DAG、任务拆分与执行顺序

### 6.1 DAG 规则

DAG 表示 Orchestrator 的调度先后，不表示原子 Skill 在内部直接调用另一个原子 Skill。

创建或修改 Skill 时必须检查：

1. 依赖是否存在；
2. 依赖是否属于正确的主 Skill；
3. 是否存在循环依赖；
4. 是否能进行稳定拓扑排序；
5. 无依赖节点和计划并行层；
6. 是否存在孤立原子 Skill 或跨主 Skill 越权依赖。

原子 Skill 不得隐式调用未声明节点。跨领域组合由 Orchestrator 或相关主 Skill 显式编排。

### 6.2 计划并行与实际执行

无依赖节点在关系上可以属于同一并行层，但并行层只表示依赖关系允许并行，不表示必须或已经并行执行。实际并行前还必须确认：

- 不存在文件写入冲突；
- 不存在共享资源冲突；
- 不存在外部重复写入风险；
- 不存在隐含顺序依赖；
- 每个执行者的上下文和输出边界清晰。

当前默认执行模式是 `serial_by_default`。项目中没有独立并行调度器，`subAgent` 只能作为经明确授权的工具协作方式，不能假设会自动启动或自动合并结果。

### 6.3 子任务拆分

任务模板支持以原子 Skill 作为子任务记录，至少记录：

- 子任务名称；
- 所属主 Skill；
- 状态；
- 依赖；
- 重试次数；
- 执行日志；
- 完成标准。

子任务拆分只有在步骤具有独立输入、输出、完成标准或错误定位价值时才成立。当前存在任务模板和历史任务记录，但没有独立的任务数据库或自动调度器。

## 7. 任务状态、共享上下文与恢复

### 7.1 状态文件

Durable Path 创建唯一任务 ID，并使用：

```text
docs/lijianxin/tasks/current/task_{任务ID}.md
```

旧的：

```text
.claude/skills/tasks/current/task_skill.md
```

仅作为兼容读取来源（旧目录已并入 `docs/lijianxin/tasks/`）。多个活动任务不得互相覆盖、合并或静默忽略。

### 7.2 状态机

```text
待执行 → 执行中 → 已完成
              ├→ 失败
              ├→ 暂停
              └→ 待恢复
```

规则：

- 失败不能直接标记为已完成；
- 重试前记录上一次失败原因和影响；
- 已完成节点不可无条件重复执行；
- 每次迁移记录原因和发生阶段；
- 依赖失败时，后续依赖节点保持阻塞；
- 恢复时不得覆盖既有结果和错误记录。

可能产生副作用的节点，恢复或重试前必须核验实际结果。无法判断是否已经产生副作用时，必须暂停并请求人工确认。

### 7.3 共享上下文

上游节点的确认结果写入任务文件共享上下文，下游优先读取共享结果，避免重复分析。建议使用节点边界标记：

```markdown
<!-- atomic-skill: skill-name -->
核心输出
<!-- /atomic-skill: skill-name -->
```

共享上下文只能传递结构化、已确认且与节点相关的信息，不应记录密码、token、凭证等敏感信息。

## 8. 结果校验与输出

### 8.1 分级校验

- `L0`：Fast Path 检查输出存在、非空、无明显错误并满足最低完成标准；
- `L1`：Durable Path 逐项检查主 Skill 和原子 Skill 的完成标准及依赖状态；
- `L2`：仅在 L1 失败、高风险或用户要求时触发反思和重新规划。

没有量化目标时，偏差标记为“不适用”，不得臆造数值。L2 默认不主动触发，触发后反思次数有限，并需记录原因和结果。

整体结果使用以下状态：

- `passed`：所有必需标准通过；
- `partial`：部分标准通过，剩余项已明确；
- `failed`：关键标准未通过；
- `blocked`：因依赖、权限或确认无法继续。

### 8.2 完成标准

主 Skill 和原子 Skill 都必须提供可观察、可检查的完成标准，包括：

- 必须完成的节点；
- 必须通过的检查；
- 允许的部分完成条件；
- 失败判定；
- 需要人工确认的情况。

禁止使用“基本完成”“处理妥当”“符合预期”等不可验证表述。

### 8.3 用户输出

固定摘要至少包含：

```text
主 Skill：{main_skill}
匹配关键词：{matched_keywords}
匹配分数：{match_score 或 unknown}
选择理由：{selection_reason}
声明依赖：{dependencies}
执行路径：{fast 或 durable}
是否持久化：{persisted}
校验级别：{validation_level}
任务 ID：{task_id 或 N/A}
状态：{status}
```

另外应说明关键产出、原子 Skill 状态、未通过项、失败/升级/重试/暂停信息以及用户下一步。

## 9. 错误、确认与安全边界

### 9.1 错误分类

| 类型 | 示例 | 默认处理 |
| --- | --- | --- |
| `validation_error` | 需求不完整、前置条件不满足 | 停止并请求补充 |
| `routing_error` | 无匹配、匹配冲突、边界不清 | 请求选择或进入 Durable Path |
| `dependency_error` | 依赖缺失、循环依赖、跨域依赖 | 执行前阻断 |
| `execution_error` | Skill 或工具执行失败 | 按策略重试或失败 |
| `permission_error` | 无权限、未确认 | 暂停，不得绕过 |
| `side_effect_error` | 写入、删除、部署结果不确定 | 恢复核验 |
| `timeout_error` | 超时、预算耗尽 | 暂停或失败 |
| `consistency_error` | 注册表、路径、版本不一致 | 阻断执行或发布 |
| `concurrency_error` | 重复执行、任务冲突 | 保留原任务并返回冲突 |
| `compatibility_error` | 版本或任务格式不兼容 | 迁移、暂停或阻断 |

失败、暂停、升级或部分完成时，必须说明当前状态、错误分类、发生阶段、受影响节点、副作用情况、是否允许重试、是否需要确认和下一步动作。

### 9.2 必须确认的操作

实际副作用发生前，必须取得用户确认：

- 删除文件、目录或 Skill；
- 覆盖已有内容；
- 修改注册表、全局配置、hooks、权限或 command；
- 修改版本文件或发布归档；
- Git `commit`、`merge`、`rebase`、`tag`、`push`；
- 生产部署；
- 数据迁移或批量修改；
- 外部系统写入；
- 无法可靠回滚的操作。

确认信息至少包括动作、影响范围、可回滚性、取消后的状态和副作用。未确认时只能规划、检查或预览；不得通过自动重试、降级路径或自主探索绕过确认。

## 10. 缺失 Skill 与自主探索

### 10.1 当前已确认能力

当前规范允许无匹配时记录 `missing_skills.md`，并判断是否能安全地通过已有 Skill 或基础工具完成任务。但项目没有名为 `autonomous-exploration`、`explorer` 或类似的独立 Skill，也没有探索预算、探索结果对象、停止控制器或轨迹记录模块。

因此，“自主探索”当前只能理解为 Claude 按安全边界调用 `Glob`、`Grep`、`Read`、`Agent`、`WebSearch` 等工具的 fallback 约定，不是自动运行能力。

### 10.2 安全处理原则

缺失能力时应按以下顺序判断：

1. 是否有已注册且职责相近的主 Skill；
2. 是否能用所属主 Skill 的既有原子步骤安全替代；
3. 是否可以仅进行只读检查、规划或预览；
4. 若不能安全完成，记录缺失能力并输出可行动的失败报告。

涉及删除、覆盖、部署、Git 写入、权限、凭证、数据迁移或其他不可逆副作用时，不得以自主探索绕过用户确认。

失败报告应包含：缺失资源、缺失功能、所在步骤、已经尝试的路径、停止原因、部分成果和用户可选的后续方案。

### 10.3 `missing_skills.md`

当前至少承担缺失能力记录功能。将其升级为完整的 Skill 演化需求库、沉淀探索模式或自动生成正式 Skill，属于待确认的未来方案，不应视为当前运行机制。

## 11. Durable 归档

仅 Durable Path 在终态（`passed`、`partial`、`failed` 或明确 `blocked`）后归档：

1. 将 `docs/lijianxin/tasks/current/task_{任务ID}.md` 移至 `docs/lijianxin/tasks/history/YYYY-MM/`；
2. 更新或创建当月任务索引；
3. 保留执行摘要、校验结果、错误日志和共享上下文；
4. 验证归档文件和索引，不要求当前目录全局为空。

Fast Path 默认不归档。归档失败时保留原任务文件和最终结果，不覆盖已有历史文件。

## 12. Skill 创建与变更规范

### 12.1 创建前设计

创建或修改 Skill 前必须明确：

- 主 Skill 或原子 Skill 的职责边界；
- 适用和不适用场景；
- 输入、输出和完成标准；
- 所属关系和依赖；
- Fast/Durable 路由条件；
- 用户确认节点和不可逆操作；
- 状态、失败、恢复和重试策略；
- 可观测性字段；
- 版本兼容和旧任务迁移影响。

### 12.2 注册一致性检查

必须检查：

```markdown
- [ ] Skill 名称、目录和注册名一致
- [ ] 主/原子归属一致
- [ ] 注册路径真实存在
- [ ] 依赖节点均已注册
- [ ] 不存在循环或孤立原子 Skill
- [ ] 已删除 Skill 不再被引用
- [ ] 相关 command 入口有效
- [ ] 注册表统计和索引信息准确
```

新增主 Skill 不要求必须创建原子 Skill；只有实际声明原子 Skill 时，才同步维护原子注册信息。

### 12.3 版本兼容

Skill 文档版本、执行规则版本和项目发布版本分别管理。改变职责边界、依赖、状态含义、完成标准、安全边界或副作用行为属于不兼容变更，必须提供迁移说明。

旧任务不得被新版本静默覆盖。不能兼容读取时应暂停并说明原因，不得强行映射并丢失信息。普通文案修订不应自动修改项目发布版本。

### 12.4 并发与幂等

- 同一任务只能有一个有效执行者；
- 同一原子 Skill 在同一任务中不得重复启动；
- 并行前检查文件、共享资源和外部写入冲突；
- 外部副作用使用任务、节点或等效标识避免重复提交；
- 重试前判断上次执行是否已经产生副作用；
- 冲突时保留原任务状态，不覆盖、不合并、不静默丢弃。

## 13. 当前协议能力与未来方案对照

### 13.1 当前已存在的目录与协议能力

以下能力已通过 Skill 文件、注册表、任务模板或配置存在，但多数属于 Markdown 协议和目录能力，实际执行依赖 Claude 按协议完成，不代表存在独立运行时：

- Orchestrator 统一入口，每次任务轻量存在性判断，安装完整性三项检查按需执行；
- 主 Skill 和原子 Skill 分层；
- 主/原子注册表；
- Fast Path / Durable Path 路由协议；
- 意图结构和主 Skill 匹配协议；
- 依赖存在性、循环依赖和稳定拓扑排序规则；
- 默认串行执行；后续规划支持多个临时子任务并行。多个主 Skill 当前采用保守的串行协作策略；主 Skill 编排原子 Skill 时可以规划串行或并行层，但当前实际执行默认仍为串行；
- Durable 任务 ID、状态文件格式和旧任务兼容读取规则；
- 断点恢复规则；
- L0/L1/L2 分级校验协议；
- Durable Path 归档流程、目录结构和任务归档文件；
- 缺失 Skill 的 Markdown 记录机制；
- 对高风险和不可逆操作的确认协议；
- Skill 创建、注册、迁移、并发和幂等规则及检查清单。

其中，意图识别、Skill 匹配、依赖检查、拓扑排序、断点恢复、结果校验和归档目前没有对应的独立程序或自动执行器；它们由 Claude 根据相关 `SKILL.md`、模板和配置执行。

### 13.2 不能当作当前运行时能力的内容

以下内容当前没有对应的独立运行时实现，不能理解为系统已经自动具备：

- 固定 `complexity < 4` / `complexity ≥ 4` 的唯一分流；
- 自动意图识别器、自动评分程序、向量检索或相似度服务；
- 自动全局跨主 Skill DAG 合并器；
- 实际并行调度器；
- Task Folding、Pattern Mining、Skill Stacking；
- 后台预探索和零等待注入；
- 独立自主探索 Agent；
- 探索预算、缓存和自动停止控制器；
- Pattern 库及自动演化为正式 Skill；
- 自动任务状态数据库、锁和恢复执行器；
- 自动归档程序；
- Hermes；
- 独立 `subskill` 运行时。

## 14. 未来规划功能

以下内容来自旧设计稿，保留为方案记录，但在确认前不纳入“当前已实现架构”。

### 14.1 多主 Skill 协同与全局 DAG

多主 Skill 全局 DAG，是指一个任务同时需要多个主 Skill 时，由 Orchestrator 统一收集各主 Skill 声明的步骤和依赖，形成一张跨主 Skill 的总任务图，再决定执行顺序、共享上下文和最终汇总方式。

该能力属于未来规划功能。后续实现时，需要明确跨主 Skill 的依赖边界、结果传递方式、冲突处理、执行顺序和用户可观测性；在实现完成前，不应将其当作当前已自动实现的能力。

### 14.2 Hermes

Hermes 属于未来规划能力。当前项目没有 Hermes 的 Skill、注册表条目、配置、command、MCP Server 或执行流程。后续需要先明确 Hermes 的定义、职责、与 Orchestrator 的关系、输入输出、权限边界和接入方式，再决定是否纳入系统。

### 14.3 自主探索与 subAgent

自主探索和 subAgent 协同属于未来规划。历史方案提出本地 Skill 扫描、subAgent 近场探索、WebSearch 远场探索和后台预探索，后续需要单独确定：

- 探索的适用范围和停止条件；
- 是否仅允许只读探索；
- subAgent 是否允许直接写入项目；
- 哪些操作必须先取得用户确认；
- 探索结果是否可以注入当前任务；
- 是否需要独立预算、缓存和执行记录。

在该能力正式设计并实现前，只能按第 10 节的安全、可解释 fallback 处理。

### 14.4 `subskill` 与 `atomic skill`

当前项目使用 `atomic-skills` 表示主 Skill 下可独立描述和校验的原子步骤。这里的 `subskill` 指在某个 Skill 的执行过程中进一步拆分出来的子 Skill，关系上类似 `agent` 与 `subagent`：它可以承担更细粒度的步骤，但不自动成为独立主 Skill。

后续规划采用“任务结构与执行资源分离”的方式：`subskill` 表示主 Skill 执行过程中由 Hermes 动态拆分出的临时任务步骤，`subagent` 表示承担具体步骤的独立执行上下文；两者不是同一层级。

推荐流程为：

```text
主 Skill：确定领域目标和完成标准
  → Hermes：拆分当前任务的临时 subskill
    → 为每个 subskill 选择执行方式
      ├── 主 Agent 直接执行
      └── SubAgent 执行
  → 主 Agent：汇总、校验和输出
```

其中：

- `subskill` 负责定义任务边界、输入、输出、依赖和完成标准；
- `subagent` 负责提供独立上下文和执行资源，适合无共享写入冲突的分析任务并行执行；
- 主 Skill 负责领域目标、最终完成标准、结果汇总和失败决策；
- Orchestrator 负责全局路由、安全边界和用户确认；
- 默认使用 `serial_by_default`，只有确认不存在文件、共享资源、外部写入和顺序冲突时才允许并行。

`subskill` 默认只存在于当前任务，不进入主 Skill 注册表、原子 Skill 注册表或独立 Skill 目录，不得绕过主 Skill、跨主 Skill 调用或执行未确认的高风险操作。只有当某个 subskill 具备稳定输入输出、独立完成标准、独立重试价值和跨任务复用价值时，才在用户确认后沉淀为正式 `atomic skill`。

Hermes、subskill 和 subagent 协同属于未来规划功能。当前项目仍以 `atomic-skills` 为正式的可复用原子能力体系，不新增独立的 subskill 注册层级。

### 14.5 预编排、Pattern 和自主升级

预编排、高频流程沉淀、Pattern 复用和自主升级属于未来规划功能。历史方案提出将高频任务固化为预设工作流，将探索结果沉淀为 Pattern，并在满足条件后升级为正式 Skill。后续实现前需要明确数据格式、审核机制、版本控制、触发条件和安全边界。

## 15. 禁止事项总表

1. 禁止绕过主 Skill，直接由用户意图触发业务原子 Skill；
2. 禁止业务原子 Skill 跨主 Skill 调用；
3. 禁止一个原子 Skill 归属多个主 Skill；
4. 禁止存在无所属原子 Skill；
5. 禁止原子 Skill 内部隐式调用其他原子 Skill；
6. 禁止使用未声明、缺失、循环或跨域依赖；
7. 禁止未确认执行不可逆操作；
8. 禁止将失败节点直接标记为成功；
9. 禁止覆盖活动任务、错误记录或历史结果；
10. 禁止注册重复、孤立或路径失效的 Skill；
11. 禁止使用不可校验的完成标准；
12. 禁止版本不兼容时静默恢复旧任务；
13. 禁止以无结构化自由文本传递关键参数；
14. 禁止用“其他”“视情况”“后续处理”等模糊表述代替明确规则；
15. 禁止以自主探索、自动重试或降级路径绕过用户确认。
